PHASE 01

Introduction to Kubernetes

Imagine you’ve built a food delivery application. At first it is one program that does everything: displays the menu, takes orders, and processes payments.

As your company grows, you split that big program into smaller, independent programs called microservices—one container for the menu, one for orders, and one for payments.

Now you face a new problem: you have 50 containers running across 10 servers. What happens if Server 3 loses power at 2:00 AM? What happens on Friday night when dinner traffic spikes 10x? Starting, restarting, networking, and scaling dozens of containers by hand is impossible.

That is **Container Orchestration**, and **Kubernetes (K8s)** is the industry-standard tool that automates it.

What is Kubernetes in one line?

Kubernetes is an open-source container orchestrator that automatically deploys, heals, networks, and scales your containers across a cluster of servers.

Docker vs. Kubernetes: Are they competitors?

Beginners often ask whether they should learn Docker or Kubernetes. In reality, they work together as two halves of the same team:

Docker · Packs the Box

Docker packages your application code and dependencies into an isolated container image and runs containers on a single computer.

Kubernetes · Runs the Fleet

Kubernetes takes the container images you built with Docker and coordinates thousands of them across many cloud servers simultaneously.

Why we need Kubernetes in DevOps (Core Use Cases)

  • Self-Healing: If a container crashes or a server dies, Kubernetes detects it within seconds and launches a fresh replacement automatically.
  • Automated Scaling: Adds more container copies during traffic spikes and removes them at night to save cloud bills.
  • Zero-Downtime Rollouts: Updates v1.0 of your app to v2.0 gradually, one pod at a time, and automatically rolls back if v2.0 has a bug.
  • Service Discovery & Load Balancing: Gives changing containers one permanent DNS name and distributes traffic evenly across healthy copies.
MENTAL MODEL

The Restaurant Idea

Before diving into the technical architecture, picture a busy restaurant. Every Kubernetes term maps cleanly to a role you already know:

Container

A sealed lunch box. Your microservice plus everything it needs, packed together.

Pod

A tray that carries the lunch box. The smallest unit Kubernetes places and moves around.

Worker Node

One kitchen (a real Linux server / EC2 instance) where trays are prepared.

Control Plane

The head office / manager. Decides which kitchen prepares which tray and replaces broken ones.

Cluster

The entire restaurant: the manager’s office (Control Plane) plus all the kitchens (Worker Nodes).

How the pieces nest inside each other

CLUSTER · the whole restaurant
WORKER NODE · a kitchen (server)
POD · a tray (gets an IP address)
CONTAINER · a lunch box Your microservice (e.g. React frontend or Orders API)

Container → Pod → Worker Node → Cluster

PHASE 02

Kubernetes Architecture: Under the Hood

Every Kubernetes cluster is divided into two halves: the Control Plane (the brains that make decisions) and the Worker Nodes (the muscles that run your containers).

1. The Control Plane (The Brains)

The Control Plane watches the cluster 24/7 and ensures reality matches your YAML files. It consists of four core components:

API Server (kube-apiserver)

The Front Desk. Every command you run with kubectl—and every message between internal components—goes through the API Server. It validates requests and is the only component allowed to talk to etcd.

etcd

The Cluster Vault / Memory. A fast, distributed key-value database that stores the entire state of the cluster: what nodes exist, what pods are running, and all ConfigMaps and Secrets.

Scheduler (kube-scheduler)

The Matchmaker. Watches for newly requested pods that don't have a server yet, checks the available CPU and RAM on every Worker Node, and assigns the pod to the best node.

Controller Manager

The Watchdog Loop. Runs background control loops (Node Controller, Deployment/ReplicaSet Controller). If you asked for 3 pods and only 2 are alive, it immediately requests a 3rd.

2. The Worker Nodes (The Muscles)

Every Worker Node (EC2 server) runs three mandatory agents so it can receive orders from the Control Plane and execute containers:

Kubelet

The Kitchen Captain. An agent installed on every node. It listens to the API Server for pod assignments, tells the Container Runtime to start the containers, and reports health back to the Control Plane.

Container Runtime

The Engine. The low-level software (usually containerd or CRI-O) that actually pulls the container image from the registry and starts/stops the Linux container process.

Kube-proxy

The Traffic Router. Runs on every node and programs Linux networking rules (iptables/IPVS) so network traffic sent to a Kubernetes Service is forwarded to healthy pods anywhere in the cluster.

PHASE 03

Essential Kubernetes Components

When you write Kubernetes YAML files or run kubectl commands, you interact with these nine fundamental objects:

Object What It Is & Why You Use It
Pod The smallest deployable unit in Kubernetes. Wraps one (or more tightly coupled) containers with a shared network IP and storage. Pods are disposable and ephemeral.
Node A physical or virtual machine (like an AWS EC2 instance) that runs your Pods.
ReplicaSet The count keeper. Ensures a specified number of identical Pod replicas (e.g., replicas: 3) are running at all times.
Deployment The higher-level manager that owns a ReplicaSet. You almost never create raw Pods or ReplicaSets directly—you create a Deployment so you get rolling updates and easy rollbacks.
Service Provides one permanent IP address, DNS name, and load balancer in front of a set of changing Pods.
Namespace Virtual folders inside a single cluster to isolate teams or environments (e.g., default, kube-system, dev, prod).
Labels & Selectors Labels are key-value sticky notes attached to Pods (e.g., app: react-ui). Selectors are how Services and Deployments find all Pods with that sticky note.
ConfigMap Stores non-sensitive configuration data (like API_URL=https://api.example.com or nginx.conf) decoupled from your container image.
Secret Stores sensitive data (database passwords, API tokens, TLS certs) separately so you never hardcode credentials inside a Dockerfile.
How Deployment, ReplicaSet, and Pods connect

Deployment manages → ReplicaSet (keeps the count at 3) which creates → 3 Pods. When you update your app image, the Deployment creates a new ReplicaSet and smoothly shifts pods over one by one.

PHASE 04

Kubernetes Installation, Setup & YAML

To practice Kubernetes, you need two things: the remote control CLI (kubectl) and a Kubernetes cluster (either free on your laptop with Minikube / Kind, or in the cloud with Amazon EKS).

1. Install kubectl & a Local Cluster (Minikube or Kind)

# Install kubectl and Minikube on macOS (Homebrew)
brew install kubernetes-cli minikube

# Start a local single-node Kubernetes cluster on your laptop (requires Docker running)
minikube start

# Verify kubectl is connected to your cluster
kubectl cluster-info
kubectl get nodes

Minikube / Kind · Local Practice

Runs a miniature Kubernetes cluster inside Docker on your laptop for free. Ideal for learning YAML syntax, Pods, and Services without spending a cent.

Amazon EKS · Cloud Production

AWS runs the Control Plane across 3 data centers and provisions real EC2 Worker Nodes and cloud Load Balancers. Connect anytime with aws eks update-kubeconfig --name myEks.

2. Basic kubectl Commands

Every kubectl command follows a simple grammar: kubectl <action> <resource> [name] [flags].

# Check cluster contexts (switch between local minikube and AWS EKS)
kubectl config get-contexts
kubectl config current-context

# List nodes, pods, deployments, and services
kubectl get nodes
kubectl get pods -A
kubectl get deployments
kubectl get services

# Apply or delete a YAML manifest file
kubectl apply -f deployment.yaml
kubectl delete -f deployment.yaml

3. Understand Kubernetes YAML Files (The 4 Mandatory Fields)

Every Kubernetes YAML manifest in the world—whether it’s a Pod, a Deployment, a Service, or an Ingress—always has the exact same four root fields:

1. apiVersion

Which version of the Kubernetes API schema to use (e.g., v1 for Pods/Services, apps/v1 for Deployments).

2. kind

What type of object you want to create (e.g., Pod, Deployment, Service, ConfigMap).

3. metadata

Identity tags for the object: its name, namespace, and labels.

4. spec

Specification (Desired State). The blueprint describing what you want inside the object: which container image, which ports, and how many replicas.

# Example: The 4 mandatory sections in a simple Pod YAML
apiVersion: v1
kind: Pod
metadata:
  name: nginx-demo
  labels:
    app: web
spec:
  containers:
    - name: nginx
      image: nginx:alpine
      ports:
        - containerPort: 80
RECAP

Quick recap: Phases 1–4

  • Docker packages an app into a container; Kubernetes orchestrates containers across many servers.
  • The Control Plane (API Server, etcd, Scheduler, Controller Manager) makes all scheduling and self-healing decisions.
  • Worker Nodes run Kubelet, containerd, and Kube-proxy to execute your Pods.
  • Deployments manage ReplicaSets, which manage Pods; Services provide a stable network endpoint using Labels & Selectors.
  • Every Kubernetes YAML file contains apiVersion, kind, metadata, and spec.
