01

The problem we’re solving

Imagine your company needs an infrastructure setup on AWS: one virtual private network (VPC), two subnets, an internet gateway, three security firewall rules, two EC2 servers, and a PostgreSQL database.

If you build this through the AWS website GUI, you will click through over 80 different web forms, drop-downs, and confirmation popups. It takes an hour. If you make one typo in a subnet mask, nothing connects.

Worse, six months later your boss asks: “Can you spin up an identical test environment for the QA team?” You have to remember and re-click all 80 steps from memory.

This is called ClickOps, and it causes human error, security leaks, and forgotten servers that cost thousands in surprise bills.

Terraform replaces manual clicking with code. You describe your entire cloud architecture in a single text file. You run one command, and Terraform creates, configures, and links every server automatically.

In one line

Terraform is a free tool that builds, updates, and deletes cloud infrastructure using code files instead of manual clicking.

02

Imperative vs Declarative

Traditional shell scripts are imperative: you give a list of step-by-step instructions. (“Click this, then wait 5 seconds, then download that, then start this.”)

Terraform is declarative: you describe the desired end result, and Terraform figures out the steps needed to get there.

The Restaurant Metaphor

Imperative (Shell Script): You walk into the kitchen and tell the chef: “Crack two eggs, turn on the stove to medium, melt butter for 30 seconds, scramble for 2 minutes, put on plate.” If the pan is already hot, it burns.

Declarative (Terraform): You tell the waiter: “I want scrambled eggs on a plate.” The waiter inspects the table. If you already have eggs, they do nothing. If you don't, they prepare them.

03

The core words you need

Terraform uses simple vocabulary. Learn these six terms and you will understand almost any Terraform codebase:

IaC (Infrastructure as Code)

Managing and provisioning cloud resources (servers, databases, networks) through machine-readable definition files rather than physical hardware configuration or manual GUI clicks.

Provider

A plugin that teaches Terraform how to talk to a specific cloud or API (e.g. AWS, Azure, Google Cloud, GitHub, Docker, Kubernetes).

Resource

A specific piece of cloud infrastructure you want to exist (e.g. an EC2 virtual machine, an S3 storage bucket, a firewall security rule).

State File (.tfstate)

Terraform’s photographic memory. A JSON ledger where it records which real cloud resources it has built and their IDs.

Plan

A dry-run preview. Terraform compares your code against what actually exists in the cloud and displays an exact list of what it will add (+), change (~), or destroy (-).

HCL (HashiCorp Config Lang)

The human-friendly language used to write Terraform files. Easier to read and write than JSON or YAML.

04

The 3 core commands: Init, Plan, Apply

Every single Terraform project in the world follows the exact same three-step heartbeat:

1. terraform init

The handshake. Terraform reads your configuration, sees that you want to talk to AWS, and downloads the official AWS provider plugin into a hidden .terraform folder.

2. terraform plan

The dry run. Checks what already exists in AWS, calculates the difference, and tells you: “Plan: 2 to add, 0 to change, 0 to destroy.” Nothing is touched yet.

3. terraform apply

The execution. Makes the real API calls to AWS, builds the actual cloud resources, and saves the resulting IDs into your local state ledger.

05

Understanding HCL syntax

Terraform files end in .tf. The syntax is composed of simple blocks. Here is what an AWS EC2 server looks like in HCL:

# Configure the AWS Provider
provider "aws" {
  region = "us-east-1"
}

# Define a virtual server resource
resource "aws_instance" "web_server" {
  ami           = "ami-0c55b159cbfafe1f0" # Ubuntu 22.04 LTS
  instance_type = "t3.micro"

  tags = {
    Name        = "Production-Web-Server"
    Environment = "Prod"
  }
}

Notice the structure of the resource block:

  • resource: The keyword saying you want something to exist.
  • "aws_instance": The resource type defined by the AWS provider.
  • "web_server": Your custom local nickname for this resource so other parts of your code can reference it.
06

The state file: Terraform’s memory

When you run terraform apply, Terraform creates an instance on AWS. AWS responds: “Created! Its ID is i-087abc1234.”

How does Terraform remember tomorrow that i-087abc1234 belongs to your project? It saves it in a file called terraform.tfstate.

Why state is critical

Without state, running terraform apply a second time would create another duplicate server. State lets Terraform know your server is already running, so it does nothing!

Golden Rule of State

Never edit terraform.tfstate by hand. If you corrupt this file, Terraform loses track of what exists in AWS and may attempt to recreate or delete everything.

08

Hands-on: Provisioning AWS with Terraform

Let's build a real, working AWS project from scratch. You will create a Virtual Private Cloud (VPC), a public subnet, an internet firewall rule, and an EC2 web server in under two minutes.

  1. Configure AWS login

    Make sure your laptop has AWS credentials configured by running aws configure and typing your Access Key and Secret Key.

  2. Create your project directory and main.tf

    Make a new folder and create main.tf:

    mkdir my-terraform-infra
cd my-terraform-infra
touch main.tf

  3. Paste this complete working configuration

    Open main.tf in your editor and paste:

    # 1. AWS Provider Configuration
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

# 2. Virtual Private Cloud (VPC)
resource "aws_vpc" "app_vpc" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true

  tags = {
    Name = "deploybook-vpc"
  }
}

# 3. Security Group (Firewall allowing HTTP and SSH)
resource "aws_security_group" "web_sg" {
  name        = "web-sg"
  description = "Allow HTTP traffic"
  vpc_id      = aws_vpc.app_vpc.id

  ingress {
    description = "Allow Web"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

# 4. EC2 Web Server
resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0" # Amazon Linux / Ubuntu
  instance_type = "t3.micro"

  tags = {
    Name = "Terraform-Web-Demo"
  }
}

# 5. Output values (Prints after apply)
output "server_id" {
  value = aws_instance.web.id
}

  4. Initialize and apply

    Run these two commands in your terminal:

    # 1. Download the AWS provider plugin
terraform init

# 2. Preview and deploy
terraform apply

    Terraform prints out the exact plan: Plan: 3 to add, 0 to change, 0 to destroy. Type yes and press Enter. Within 45 seconds, all resources exist in your AWS account!

09

Cleaning up with terraform destroy

In cloud computing, forgotten test servers cause expensive bills. One of Terraform's superpowers is complete, flawless teardown.

When you're finished practicing for the day, type:

# Delete everything defined in your main.tf
terraform destroy

Terraform inspects its state file, identifies every resource it created, determines the reverse dependency order (deletes the server first, then the firewall, then the VPC), and cleanly wipes them all out. Zero orphaned resources, zero surprise bills.

10

Golden rules for production

Use Remote State (S3 + DynamoDB)

Never commit terraform.tfstate to GitHub! Store it in an encrypted AWS S3 bucket, and use DynamoDB for state locking so two teammates don't apply at the same time.

Always run terraform plan

Never run apply -auto-approve blindly in production. Always inspect the plan output to confirm you aren't accidentally destroying a live production database!

11

Commands cheatsheet

terraform init

Initializes the directory and downloads required provider plugins.

terraform plan

Calculates the diff between code and reality; shows proposed changes.

terraform apply

Executes the plan to provision or update real cloud resources.

terraform destroy

Tears down and deletes all resources managed by the state file.

terraform fmt

Auto-formats your .tf files with canonical spacing and alignment.

terraform validate

Checks your code for syntax errors and internal consistency.

12

Quick recap

  • Infrastructure as Code (IaC) replaces manual clicking with version-controlled text files.
  • Terraform is declarative: you declare what you want, Terraform figures out how to build it.
  • Providers are plugins that translate Terraform code into cloud API requests (AWS, Azure, GCP).
  • The 3 core commands are init (download plugins), plan (preview changes), and apply (build).
  • The .tfstate file is Terraform's memory; protect it and store it in remote cloud storage.
  • Run terraform destroy when done to cleanly delete all test resources and avoid cloud bills.
If you remember one thing

Never build cloud infrastructure with manual clicks twice. Define it in Terraform once, and you can recreate it anytime with a single command.
