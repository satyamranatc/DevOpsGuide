Beginner’s guide

Kubernetes on AWS,
explained simply.

Pods, nodes, servers and EKS. What they are, how they fit together, and how your microservices end up running on them. No jargon, one picture.

01

The problem we’re solving

Imagine you’ve built a food delivery app. At first it’s one program that does everything: shows the menu, takes orders, handles payments.

As the app grows, that one big program becomes hard to change. A small fix to payments might break the menu. So you split it into small programs, each with one job. One for the menu. One for orders. One for payments.

These small programs are called microservices.

Now you have a new problem. Lots of little programs need to run on lots of computers. They need to stay online, talk to each other, and handle more visitors on busy evenings. Doing that by hand is exhausting.

That’s where Kubernetes comes in.

In one line

Kubernetes is a free tool that looks after your programs for you: it starts them, keeps them running, and adds more when you get busy.

02

The restaurant idea

The new words are easier when you picture a restaurant. Keep this table in mind. We’ll go through each word properly next.

Microservice

One dish on the menu. A small program with one job.

Container

A sealed lunch box. Your program plus everything it needs, packed together.

Pod

A tray that carries a lunch box to the table. The smallest thing Kubernetes moves around.

Node

One kitchen. A real computer where trays get prepared. Another word for it: server.

Cluster

The whole restaurant: all the kitchens together, plus the manager.

Control plane

The manager. Decides which kitchen makes what, and replaces anything that goes wrong.

AWS

The landlord. Rents you kitchens (computers) so you don’t have to buy any.

EKS

A manager hired through AWS, so you don’t have to run one yourself.

03

Container

Your program needs certain things to work: the right version of its language, some files, some settings. On your laptop it works. On another computer it breaks because something is missing.

A container fixes this by packing your program together with everything it needs. Wherever it goes, it behaves the same.

Think of it as

A sealed lunch box. Whoever opens it, anywhere, finds the same meal inside.

Most people make containers with a tool called Docker. You don’t need to learn it today. Just remember: one microservice, one container.

04

Pod

Kubernetes doesn’t move containers around directly. It wraps them in a pod.

Most of the time a pod holds just one container. So for a beginner it’s fine to think: a pod is your running microservice.

Think of it as

A tray carrying the lunch box. The kitchen doesn’t handle loose lunch boxes, only trays.

Pods are disposable. If one crashes, Kubernetes doesn’t fix it. It throws it away and starts a fresh one. That’s normal, and it’s a good thing, because your app heals itself.

05

Node and server

A server is just a computer that lives in a big data centre and stays on all day. It has no screen. Other computers connect to it.

In Kubernetes, a server that runs your pods is called a node. They’re the same thing. “Server” is the everyday word. “Node” is the Kubernetes word.

Think of it as

A kitchen. It has a limited amount of space and power, so it can only prepare so many trays at once.

When one node is full, Kubernetes puts new pods on another. This is how you grow without rewriting anything.

How the pieces nest

This is the most useful mental picture. Each thing sits inside the next.

CLUSTER · the whole restaurant
NODE · a kitchen (server)
POD · a tray
CONTAINER · a lunch box Your microservice, for example “orders”

Container → Pod → Node → Cluster

06

Cluster and the manager

A group of nodes working together is a cluster. It’s your whole restaurant.

Someone has to decide which kitchen prepares which tray. That’s the job of the control plane, the manager of the restaurant.

The manager does three things all day:

  • Decides. “The orders tray goes to kitchen 2, it has space.”
  • Watches. It keeps checking that everything is still running.
  • Fixes. If a tray falls on the floor, it sends out a new one.

You don’t cook anything yourself. You just tell the manager what you want, and it makes it happen.

07

Deployment and Service

Two more words and you’ll know the basics.

Deployment

A standing order. “Always keep 3 trays of orders ready.” If one disappears, the manager makes another to get back to 3.

Service

The front counter. Trays come and go, but customers always use the same counter. It hands each request to a tray that’s ready.

Why do you need a Service? Because pods keep being replaced, and each new one gets a new address. The Service gives other programs one steady name to use, so nothing breaks when pods change.

08

Where AWS and EKS fit

AWS (Amazon Web Services) is a company that rents out computers over the internet. Instead of buying servers and keeping them in a cupboard, you rent them by the hour and hand them back when you’re done.

You can install Kubernetes yourself on rented computers, but running the manager is hard work. It has to be set up carefully, kept up to date, and never allowed to go down.

EKS (Elastic Kubernetes Service) is AWS saying: “We’ll run the manager for you.”

AWS looks after

The control plane. Setting it up, keeping it healthy, updating it, and making sure it doesn’t fail.

You look after

Your microservices, and how many servers you want for them to run on.

Where do the servers come from?

You have two easy choices. You can rent servers from AWS (they’re called EC2) and let EKS manage them for you. Or you can pick Fargate, where AWS handles the servers completely and you only think about pods.

Heads-up on cost: EKS charges a small hourly fee for the manager, plus the cost of the servers you use. Remember to delete a practice cluster when you’re finished.

10

Deploying, step by step

Here is the journey from “it works on my laptop” to “it’s running on EKS”.

  1. Put each microservice in a container

    Use Docker to pack your menu, orders and payments programs into their own lunch boxes. These are called images.

  2. Store the images on AWS

    AWS has a storage place just for them, called ECR. Think of it as the pantry where all your lunch boxes wait until they’re needed.

  3. Create your EKS cluster

    Ask AWS for a cluster. It builds the manager, and you pick the servers. A tool called eksctl does this with a single command.

  4. Tell Kubernetes what you want

    You write a short note saying which image to run and how many copies you want. Here’s what one looks like, so you’ve seen it once:

    # "Keep 3 copies of my orders app running"
name: orders
copies: 3
image: my-pantry/orders:1.0

    The real file uses slightly different words, but the idea is exactly this. Kubernetes reads your note and makes it true.

  5. Open the front door

    Add a load balancer so people on the internet can reach your app. It shares visitors across your pods, so no single one gets overwhelmed.

11

How to make and control EKS

You know the theory: EKS is a restaurant manager hired through AWS, and pods are dishes cooking in server kitchens. But how do you actually build this on AWS, and what steering wheel do you use to control it day to day?

The good news: you never have to log into dozens of cloud servers or touch real hardware. You control everything right from your laptop using two small tools.

The mental model

Think of AWS like a contractor that builds your restaurant. You give them one order to build the building (eksctl). Once it’s open, you sit outside with a walkie-talkie (kubectl) and tell the manager what to do.

The two tools you need on your laptop

Before making a cluster, you install two free command-line helpers on your computer:

eksctl · The Builder

A tool made by AWS and Weaveworks. You use it once or twice: to build the entire cluster from scratch, or tear it down when you're done.

kubectl · The Remote Control

The official Kubernetes remote control (pronounced kube-control). You use this every day to check health, launch apps, and read logs.

Step 1 · Make the cluster in AWS (One command)

Make sure you have logged into your AWS account with aws configure. Then run this single command in your terminal:

# Create an EKS cluster with 2 worker servers
eksctl create cluster \
  --name my-cluster \
  --region us-east-1 \
  --nodes 2 \
  --node-type t3.medium

Now grab a cup of coffee. It takes about 12 to 15 minutes. That isn’t broken or frozen — behind the scenes, AWS is doing an enormous amount of heavy lifting for you:

  • Builds the manager’s office: AWS sets up 3 independent control plane servers across separate physical buildings (Availability Zones). If one building loses power, your cluster never blinks.
  • Rents 2 server kitchens: AWS launches 2 EC2 instances (the nodes) where your containers will actually run.
  • Lays private roads & security guards: Creates a Virtual Private Cloud (VPC), firewalls, and subnets so your microservices can talk securely.
  • Pairs your remote control: Automatically hands the digital keycard to your laptop so kubectl is immediately ready to give orders.
Can you also use the AWS website?

Yes! In the AWS Web Console, you can search for EKS and click Create cluster. But you’ll have to answer 20+ questions about networking, security roles, and subnets. eksctl picks safe, battle-tested defaults for you in one line.

Step 2 · Take the wheel (Connecting your remote)

If you ever switch laptops or created the cluster in the AWS web console, your laptop needs the "keycard" to talk to your cluster. You grab it with this one command:

# Pair your laptop's kubectl with your AWS cluster
aws eks update-kubeconfig --region us-east-1 --name my-cluster

This saves a secure login token in a hidden file on your computer (~/.kube/config). From this second on, whenever you type kubectl, it automatically talks to your AWS cluster in the cloud.

Step 3 · Controlling EKS (Your daily buttons)

Now that your restaurant is open and your walkie-talkie is connected, what does "controlling EKS" actually look like? Here are the 6 buttons you'll press most often:

kubectl get nodes

Check the kitchens. Shows all your servers and confirms their status is Ready.

kubectl get pods

Check the dishes cooking. Lists all running pods, whether they’re healthy (Running), starting (ContainerCreating), or crashing (CrashLoopBackOff).

kubectl apply -f app.yaml

Give the manager an order. Hands your YAML file to Kubernetes. The manager reads what you want and deploys or updates your pods automatically.

kubectl scale deployment orders --replicas=5

Rush hour volume control. Instantly tells the manager: “Keep 5 copies of the orders app running instead of 2.”

kubectl logs <pod-name>

Listen to what your app is saying. Prints out whatever your Node, Python, or Go code logged to the screen (errors, incoming requests, or startup messages).

kubectl describe pod <pod-name>

The doctor’s inspection. If a pod won’t start, this gives you the exact timeline of events at the bottom (e.g. “Downloaded image”, or “Out of memory”).

Step 4 · Turning it off (Don’t leave the lights on!)

AWS charges about $0.10 an hour (~$73 a month) just to keep the EKS manager running, plus whatever the 2 server nodes cost. For a company this is pocket change, but for a learner practicing on a weekend, you don’t want surprise bills.

When you’re done practicing for the day, tear the whole restaurant down with one command:

# Delete the cluster and all servers so AWS stops charging you
eksctl delete cluster --name my-cluster --region us-east-1

In about 10 minutes, AWS cleanly shuts down the servers, deletes the networking cables, dissolves the manager, and stops the billing meter.

12

Deploy a React app with the AWS GUI

If you prefer clicking through visual dashboards instead of typing terminal commands, you can build your entire Amazon EKS cluster and deploy your React (or MERN) frontend directly inside the AWS Management Console.

Here is the full, click-by-click journey from your local React project to a live URL running across multiple AWS cloud servers.

The GUI Roadmap

We will: (1) Store your React container in AWS ECR, (2) Create 2 IAM security badges, (3) Click Create cluster in the EKS Console, (4) Add 2 server nodes in the Compute tab, (5) Tell Kubernetes to launch your pods, and (6) Open your live AWS Load Balancer URL.

  1. Containerize your React app and push to AWS ECR

    First, wrap your React app in a high-performance, lightweight production web server (Nginx). In your React project root directory, create a file named Dockerfile:

    # Stage 1: Build the React static production bundle
FROM node:18-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build

# Stage 2: Serve static files with ultra-fast Nginx
FROM nginx:alpine
COPY --from=build /app/build /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

    Now open the AWS Management Console in your browser:

    • Search for ECR (Elastic Container Registry) in the top search bar and click Repositories.
    • Click the orange Create repository button, keep visibility as Private, name it my-react-app, and click Create repository.
    • Click on your newly created repository name in the list, then click the View push commands button at the top right.
    • AWS opens a popup with 4 exact commands containing your account ID. Run them in your terminal to build, tag, and upload your container image into your private AWS pantry.

  2. Create the 2 required IAM Security Roles

    Before launching EKS, AWS requires two security badges (IAM roles) so that the EKS manager and your EC2 servers have permission to coordinate:

    Role 1: Cluster Manager Role

    1. Open IAM Console → Roles → Create role.
    2. Select AWS service → Use case: EKS - Cluster.
    3. Policy is automatically checked: AmazonEKSClusterPolicy.
    4. Name it eksClusterRole and click Create role.

    Role 2: EC2 Node Worker Role

    1. In Roles, click Create role → Service: EC2.
    2. Search and attach these 3 policies:
    • AmazonEKSWorkerNodePolicy
    • AmazonEC2ContainerRegistryReadOnly (to pull your ECR image)
    • AmazonEKS_CNI_Policy
    3. Name it eksNodeRole and click Create role.

  3. Create the EKS Cluster in the AWS Web Console

    Now summon the restaurant manager through the AWS GUI:

    • Search for EKS in the AWS Console search bar and click Clusters → Add cluster → Create.
    • Step 1 (Configure cluster): Name your cluster react-eks-cluster, select Kubernetes version (e.g. 1.30), and choose eksClusterRole in the Cluster service role dropdown. Click Next.
    • Step 2 (Specify networking): Choose your VPC (the default VPC works great), select at least 2 public subnets in different Availability Zones (e.g. us-east-1a and us-east-1b), and under Cluster endpoint access select Public and private.
    • Click Next through the default networking add-ons (CoreDNS, kube-proxy, VPC CNI), review your settings, and click Create.

    The cluster status will display Creating. It takes about 8 to 12 minutes for AWS to configure the high-availability manager across 3 physical facilities. Grab a coffee while it finishes!

  4. Add Worker Nodes (Compute) via the EKS Tab

    Once your cluster status turns green (Active), it's time to launch the server kitchens where your React pods will actually live:

    • Click into react-eks-cluster and switch to the Compute tab.
    • Under the Node groups section, click Add node group.
    • Step 1 (Configure node group): Name it react-node-group and choose eksNodeRole from the Node IAM Role dropdown. Click Next.
    • Step 2 (Compute and scaling): Keep Amazon Linux 2, choose instance type t3.medium (or t3.small for testing), and set Scaling: Desired = 2, Minimum = 1, Maximum = 3.
    • Click Next, confirm the subnets, and click Create. Within 3 to 4 minutes, your two servers will show status Active.

  5. Deploy your React App to the Cluster

    Now that your cluster and server nodes are live in the AWS GUI, pair your laptop once so your command line can talk to the new cluster:

    # Link your kubectl remote control to your new AWS GUI cluster
aws eks update-kubeconfig --region us-east-1 --name react-eks-cluster

    Create a deployment file named react-app.yaml (replace the image URL with your real ECR repository URI from Step 1):

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: react-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: react-app
  template:
    metadata:
      labels:
        app: react-app
    spec:
      containers:
      - name: react-app
        image: <YOUR-ACCOUNT-ID>.dkr.ecr.us-east-1.amazonaws.com/my-react-app:latest
        ports:
        - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: react-service
spec:
  type: LoadBalancer
  selector:
    app: react-app
  ports:
  - protocol: TCP
    port: 80
    targetPort: 80

    Apply your recipe to the cluster:

    # Hand your recipe to Kubernetes
kubectl apply -f react-app.yaml

  6. See your live site via the AWS Load Balancer (GUI)

    Because your service configuration specified type: LoadBalancer, Kubernetes automatically requested AWS to provision an internet-facing Elastic Load Balancer (ELB).

    • In the AWS Console, search for EC2 and click Load Balancers in the left sidebar menu under Load Balancing.
    • You will see an active Load Balancer created automatically with a name like a78bc....
    • Select it and copy the DNS name in the summary card below (e.g. k8s-default-reactapp-12345.us-east-1.elb.amazonaws.com).
    • Paste the DNS name into your browser tab: Your React app is live, load-balanced across multiple AWS EC2 instances!
    Prefer checking via terminal?

    Run kubectl get svc react-service — the address listed under the EXTERNAL-IP column is the exact same AWS Load Balancer URL.

  7. Clean up in the AWS Console (Stop the billing meter)

    When you're finished testing for the day, clean up so AWS stops billing you:

    • Run kubectl delete service react-service in terminal to release and terminate the AWS Load Balancer immediately.
    • In the EKS Console → Clusters → react-eks-cluster → Compute tab, select your node group and click Delete.
    • Once the nodes are terminated, click Delete cluster at the top right of the EKS Console.
    • In the ECR Console, delete your repository if you no longer need the stored Docker image.
13

Quick recap

  • Microservices are small programs, each with one job.
  • A container packs one program with everything it needs.
  • A pod wraps the container so Kubernetes can run it.
  • A node is a server where pods run.
  • A cluster is all your nodes plus the manager (the control plane).
  • A Deployment keeps the right number of pods alive. A Service gives them one steady address.
  • AWS rents you the servers. EKS runs the manager for you.
If you remember one thing

You describe what you want. Kubernetes keeps it that way. EKS means AWS looks after the part that does the keeping.
