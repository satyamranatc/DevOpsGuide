01

Where AWS and Amazon EKS fit

In Part 1 (Kubernetes Basics), you learned that a Kubernetes cluster has two parts: the Control Plane (the manager) and the Worker Nodes (the server kitchens).

You can install Kubernetes yourself on rented EC2 servers, but running the Control Plane is hard work—you have to configure high-availability etcd databases across multiple data centers, patch security vulnerabilities, and ensure the API Server never goes down.

Amazon EKS (Elastic Kubernetes Service) is AWS saying: “We’ll run the Control Plane for you.”

AWS looks after

The Control Plane across 3 Availability Zones—setting it up, scaling the API Server, backing up etcd, and replacing unhealthy master nodes automatically.

You look after

Your Worker Nodes (via Managed Node Groups, Auto Mode, or Serverless Fargate) and the YAML manifests for your microservices.

EKS CLUSTER · Control Plane managed by AWS
EC2 WORKER NODE · Managed Node Group or Auto Mode
POD · Scheduled & self-healed
CONTAINER · Pulled from Amazon ECR Your React frontend or Node/Go microservice

03

Creating & Controlling EKS

You can create an EKS cluster in one terminal command with eksctl, or click through the AWS Web Console, and then control it from your laptop with kubectl:

# Option A: Create a complete EKS cluster + 2 EC2 nodes in one command
eksctl create cluster \
  --name my-cluster \
  --region us-east-1 \
  --nodes 2 \
  --node-type t3.medium

# Connect your local kubectl to an existing EKS cluster
aws eks update-kubeconfig --region us-east-1 --name my-cluster

# Delete the cluster when finished practicing so AWS stops charging ($0.10/hr)
eksctl delete cluster --name my-cluster --region us-east-1

04

Deploy a React App with the AWS GUI

If you prefer setting up your cluster through the AWS Management Console before deploying with kubectl, follow this 5-step checklist:

  1. Build & Push React Image to Amazon ECR

    Use a multi-stage Dockerfile (node:22-alpine to build /app/dist, then nginx:alpine to serve on port 80). In the AWS Console, open ECR → Create repository (my-react-app), click View push commands, and run the 4 commands to upload your image.

  2. Create the 2 IAM Roles

    In IAM → Roles, create: (1) eksClusterRole with AmazonEKSClusterPolicy, and (2) eksNodeRole (EC2 service) with AmazonEKSWorkerNodePolicy, AmazonEC2ContainerRegistryReadOnly (required to pull from ECR!), and AmazonEKS_CNI_Policy.

  3. Create the EKS Cluster & Node Group

    In EKS → Clusters → Create, select eksClusterRole and public/private endpoint access. Once Active, open the Compute tab and either enable EKS Auto Mode or click Add node group with eksNodeRole and 2 t3.medium instances.

  4. Apply Deployment & LoadBalancer Service

    Run aws eks update-kubeconfig --name <cluster>, then apply your Deployment and type: LoadBalancer Service YAML (Ensure public VPC subnets have tag kubernetes.io/role/elb = 1).

  5. Clean Up in the Right Order ($0 Surprise Bill Rule)

    Always run kubectl delete svc <service-name> first so Kubernetes deletes the AWS Load Balancer, then delete the Node Group, and finally delete the EKS Cluster.

PHASE 09

Troubleshooting Kubernetes & Pod Lifecycle

Every Pod moves through a strict lifecycle: Pending (waiting for a Node) → ContainerCreating (pulling image & mounting volumes) → Running (active) → Succeeded / Failed.

When something breaks, follow this diagnostic sequence:

# 1. View all Pods and check the STATUS and RESTARTS columns
kubectl get pods -A

# 2. Inspect Pod events (scheduling failures, image pull errors, failed probes)
kubectl describe pod <pod-name>

# 3. Check application stdout/stderr logs (and --previous if it just crashed)
kubectl logs <pod-name>
kubectl logs <pod-name> --previous

# 4. Troubleshoot Service connectivity (verify Endpoints list is not empty!)
kubectl describe service <service-name>
kubectl get endpoints <service-name>

How to Fix the 4 Most Common Errors

ImagePullBackOff / ErrImagePull
Cause: Wrong image URI/tag, or the Worker Node IAM Role lacks AmazonEC2ContainerRegistryReadOnly permission to pull from private ECR.
Fix: Run kubectl describe pod <name>, check the exact image URL, and verify ECR IAM permissions.
CrashLoopBackOff
Cause: The container starts, crashes immediately (bad env var, uncaught exception, or port conflict), and Kubelet keeps restarting it.
Fix: Run kubectl logs <name> --previous to read the exact crash stack trace.
Pod Stuck in Pending
Cause: Scheduler cannot find a Node with enough free CPU/Memory for your requests, or no Worker Nodes are Ready.
Fix: Run kubectl get nodes and kubectl describe pod <name>; scale up your node group or lower resource requests.
Service Not Reachable
Cause: The Service selector labels don't match the Pod's metadata.labels, or targetPort doesn't match the container's listening port.
Fix: Run kubectl get endpoints <svc>. If ENDPOINTS is <none>, fix the label selector in your Service YAML.
PHASE 10

Kubernetes in the DevOps Ecosystem

In real production teams, Kubernetes connects directly to your container registry, autoscalers, package managers, CI/CD pipelines, and observability stack:

1. Horizontal Pod Autoscaler (HPA) & Cluster Scaling

Instead of manually running kubectl scale during traffic spikes, an HPA watches average CPU or memory usage (via Kubernetes Metrics Server) and automatically adjusts the number of Pod replicas between a minimum and maximum:

# Automatically scale react-web between 2 and 10 pods when CPU exceeds 70%
kubectl autoscale deployment react-web --cpu-percent=70 --min=2 --max=10

# Inspect active HPA status and current CPU load
kubectl get hpa

2. Helm (The Kubernetes Package Manager)

Installing complex software like Prometheus, NGINX Ingress, or Cert-Manager requires 20+ YAML files. Helm bundles all those templates into a single reusable package called a Chart (just like apt or npm for Kubernetes):

# Add a Helm repository and install Prometheus + Grafana in one command
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm install monitoring prometheus-community/kube-prometheus-stack

3. CI/CD & Observability Integration

CI/CD with GitHub Actions

On every git push, GitHub Actions builds your Docker image, pushes it to Amazon ECR, and runs kubectl set image (or ArgoCD syncs it) for a zero-downtime rollout.

Prometheus & Grafana

Prometheus scrapes metrics from Kubelet and cAdvisor across all nodes, and Grafana visualizes cluster CPU, Pod restarts, and memory saturation in real time.

RECAP

Quick recap: Phases 9–10

  • Amazon EKS runs the Kubernetes Control Plane across 3 Availability Zones so you only manage worker nodes and apps.
  • Diagnose any Pod error in seconds with kubectl get pods, kubectl describe pod, and kubectl logs --previous.
  • Horizontal Pod Autoscaler (HPA) scales Pod replicas automatically based on live CPU/memory metrics.
  • Helm packages multi-file Kubernetes apps into reusable Charts.
  • Always delete LoadBalancer Services before deleting an EKS cluster to avoid orphaned AWS ELB charges.
