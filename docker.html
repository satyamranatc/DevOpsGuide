Beginner’s guide

Docker,
explained simply.

Images, containers and the handful of commands you really need. Then we build and run a real app, start to finish.

01

The problem we’re solving

You build an app on your laptop and it works perfectly. You send it to a friend, or a server, and it breaks. Different version of the language, a missing file, a different setting.

Every developer has said the same sentence: “But it works on my machine!”

Docker fixes this. It packs your app together with everything it needs into one sealed package. That package runs the same way on your laptop, your friend’s laptop, and any server in the world.

In one line

Docker packs your app and everything it needs into one box that runs the same everywhere.

02

The lunch box idea

Think of cooking a meal and packing it for a trip. These words fit together the same way.

Dockerfile

The recipe. A short text file listing the steps to prepare your app.

Image

The frozen, ready-made meal. Built from the recipe. It never changes, and you can make as many copies as you like.

Container

A meal being eaten right now. A running copy of an image.

Registry

A shop for ready-made meals. Docker Hub is the most popular one. You download images from it, or upload your own.

Port

A door on the box. It lets traffic from outside reach the app inside.

Volume

A shelf outside the box where data is kept, so it survives when the box is thrown away.

The key difference

An image is the recipe’s finished meal, sitting in the freezer. A container is that meal, heated up and being served. One image can run as many containers as you want.

03

Install and test

Download Docker Desktop from docker.com. It works on Mac, Windows and Linux. Open it once so it starts, then open a terminal and check that it’s working.

# check Docker is installed
docker --version

# run Docker's tiny test container
docker run hello-world

If you see a “Hello from Docker!” message, everything is ready. Behind the scenes, Docker couldn’t find the hello-world image on your computer, so it downloaded it from Docker Hub, then ran it.

04

Build a real app

Let’s put a tiny website into a container. You’ll make three files in one new folder. Nothing else is needed, and you don’t even have to install Node on your computer, because Docker brings it along.

Step 1 · Make the app

Create a file called app.js. It’s a tiny web server that says hello.

// app.js
const http = require('http');

http.createServer((req, res) => {
  res.end('Hello from my first container!\n');
}).listen(3000);

console.log('Listening on port 3000');

Step 2 · Write the recipe

Create a file called exactly Dockerfile, with no file ending. Each line is one step.

# Dockerfile
# 1. Start from a small ready-made box that has Node inside
FROM node:20-alpine

# 2. Choose a folder inside the box to work in
WORKDIR /app

# 3. Copy our app into the box
COPY app.js .

# 4. Note that the app uses port 3000
EXPOSE 3000

# 5. The command to run when the box starts
CMD ["node", "app.js"]

Step 3 · Build the image

Open a terminal in that folder. This turns the recipe into an image and names it hello-app. The dot at the end means “use this folder”.

docker build -t hello-app .

Step 4 · Run it

Start a container from the image.

docker run -d -p 8080:3000 --name hello hello-app

Here’s what each piece means:

  • -d runs it in the background, so your terminal stays free.
  • -p 8080:3000 connects port 8080 on your computer to port 3000 inside the box. Read it as outside:inside.
  • --name hello gives the container a friendly name.
  • hello-app is the image to run.

Step 5 · See it working

Open http://localhost:8080 in your browser, or use this:

curl http://localhost:8080
# Hello from my first container!

You just ran an app from a container. To look around, use these:

# is it running?
docker ps

# what has the app printed?
docker logs hello

# step inside the box and look around
docker exec -it hello sh

# stop it, then remove it
docker stop hello
docker rm hello
05

The whole picture

Follow the arrows: a recipe becomes an image, and an image becomes as many running containers as you like. Images can also be stored in a registry and shared.

06

Every command you need

Docker has hundreds of options, but day to day you’ll use about fifteen. Here they are, grouped by what you’re trying to do.

Images

docker build -t name .

Build an image from the Dockerfile in this folder.

docker images

List the images on your computer.

docker pull name

Download an image from a registry.

docker push name

Upload your image to a registry.

docker rmi name

Delete an image.

docker tag old new

Give an image another name or version.

Running containers

docker run image

Create and start a container from an image.

docker run -d image

Same, but in the background.

docker run -p 8080:3000 image

Open a port: your computer’s 8080 to the container’s 3000.

docker run --name x image

Give the container a name.

docker run -e KEY=value image

Pass a setting into the container.

docker run --rm image

Delete the container automatically when it stops.

Looking after containers

docker ps

Show running containers. Add -a to see stopped ones too.

docker logs name

Show what the app has printed. Add -f to follow live.

docker exec -it name sh

Open a shell inside a running container.

docker stop name

Stop a container politely.

docker start name

Start a stopped container again.

docker restart name

Stop and start it again.

docker rm name

Delete a stopped container.

Tidying up

docker system prune

Delete stopped containers and unused leftovers.

docker login

Sign in to Docker Hub so you can push images.

A handy habit

Stuck on any command? Add --help to it, for example docker run --help. Docker will list every option.

07

Docker Compose

Real apps often need more than one container, such as a website and a database. Typing a long docker run for each one gets tiring.

Docker Compose lets you describe everything in one file and start it all with one command. Create compose.yaml in the same folder as before:

# compose.yaml
services:
  web:
    build: .
    ports:
      - "8080:3000"

This says: “Build the app from this folder, and open port 8080.” Now run it:

# build and start everything in the background
docker compose up -d

# see what's running
docker compose ps

# watch the logs
docker compose logs -f

# stop and remove everything
docker compose down

When you add a database later, you’ll just add another block under services, and the same up command starts both.

08

Keeping your data

Here’s something that surprises beginners. When you delete a container, everything inside it is deleted too. That’s fine for an app, but not for a database.

The fix is a volume, a shelf outside the box. The container reads and writes to it, but the shelf stays even when the container is gone.

# create a volume called mydata
docker volume create mydata

# attach it to a container at /data
docker run -d -v mydata:/data --name keeper hello-app

# list your volumes
docker volume ls

Anything saved in /data inside that container now survives, even if you delete and recreate the container.

09

When things go wrong

These are the problems almost everyone meets in the first week.

“Cannot connect to the Docker daemon”

Docker Desktop isn’t running. Open it and wait until it says it’s started.

“Port is already allocated”

Something else is using that port. Pick another, such as -p 8081:3000, or stop the old container.

“The name is already in use”

An old container still has that name. Run docker rm hello first.

Container stops straight away

The app inside crashed. Run docker logs name to see why.

Page won’t load

Check the port order. It’s outside:inside, and the inside number must match what your app listens on.

10

Quick recap

  • A Dockerfile is the recipe. docker build turns it into an image.
  • An image never changes. docker run starts a container from it.
  • -p outside:inside opens a door so you can reach the app.
  • docker ps, logs, exec, stop and rm cover most daily work.
  • A registry stores images so others can pull them.
  • Compose runs many containers from one file.
  • A volume keeps data safe when a container is removed.
If you remember one thing

Write the recipe once, build the image once, then run it anywhere. That’s the whole point of Docker, and it’s exactly what Kubernetes and EKS do next, at a much bigger scale.
