Step 1: Check Your Tools

First, check whether the required tools are installed on your terminal (Mac/Linux). Open your command line and run:

terminal — tool check 
aws --version
kubectl version --client
docker --version

What do these tools do?

Tool Purpose
aws Interact with AWS cloud services (EKS, ECR, IAM, EC2, VPC).
kubectl The standard Kubernetes CLI used to control pods, nodes, deployments, and services.
docker Build, tag, and manage local container images before pushing to registries.
eks AWS-managed Kubernetes service; accessed through AWS CLI tools and kubectl.
Missing a tool on Mac?

If any command prints command not found, install it using Homebrew:
brew install awscli kubernetes-cli
For Docker, download Docker Desktop or run brew install --cask docker.

02

Step 2: Configure AWS CLI

Before communicating with your EKS cluster, your terminal must know who you are and have permissions granted via AWS IAM credentials.

Check your active AWS identity

Run sts get-caller-identity to verify your Account ID and IAM User/Role:

bash — check identity 
aws sts get-caller-identity
Sample Output { "UserId": "AIDAJ...", "Account": "123456789012", "Arn": "arn:aws:iam::123456789012:user/admin" }

List your configured AWS region

bash — check region 
aws configure get region

If your AWS CLI isn't configured yet or returns an authentication error, run:

bash — setup credentials 
aws configure

The interactive prompt will request four items:

  • AWS Access Key ID: Your 20-character key starting with AKIA...
  • AWS Secret Access Key: Your private 40-character secret.
  • Default region: The region where your EKS cluster lives (e.g. ap-south-1, us-east-1).
  • Default output format: Enter json.
🔒 Security Tip

Never share your AWS credentials, paste them in public chats, or commit them to GitHub repositories. Use AWS IAM credentials with least-privilege policies.

03

Step 3: List Your EKS Clusters

List all active and creating EKS clusters within your current default region:

bash — list clusters 
aws eks list-clusters

Get detailed status of a cluster

Query the status of your specific cluster (replace myEks with your cluster name):

bash — describe cluster status 
aws eks describe-cluster \
  --name myEks \
  --query "cluster.status"
Expected output when cluster is ready "ACTIVE"

Check or specify explicit region

If aws eks list-clusters returns an empty list {"clusters": []}, check what region your CLI is searching:

bash — check region 
aws configure get region

You can also query the cluster by explicitly passing the --region flag:

bash — explicit region 
aws eks list-clusters --region ap-south-1

Replace ap-south-1 with the region where your cluster was launched (e.g. us-east-1, eu-west-1).

Step 4: Connect kubectl to EKS

This is one of the most important commands in the entire EKS workflow. It downloads the cluster certificate authority, endpoint URL, and generates authentication tokens in your local ~/.kube/config file.

bash — update-kubeconfig 
aws eks update-kubeconfig --name myEks
Sample Success Message Updated context arn:aws:eks:ap-south-1:123456789012:cluster/myEks in ~/.kube/config

If your cluster is in a different region than your default CLI config, specify the region flag:

bash — update-kubeconfig with region 
aws eks update-kubeconfig --region ap-south-1 --name myEks

Verify the connection

Verify that kubectl can reach the Kubernetes API endpoint:

bash — cluster-info 
kubectl cluster-info

Check which cluster your terminal is connected to

bash — current-context 
kubectl config current-context

Check whether Kubernetes can communicate with worker nodes

bash — get nodes 
kubectl get nodes

If configured correctly, you will see your worker nodes with status Ready.

Step 5: Essential Kubernetes Commands

These are the core commands you will use daily while operating and inspecting applications on EKS. They are organized across the 4 foundational Kubernetes primitives: Nodes, Pods, Deployments, and Services.

1. Nodes

A node is a worker server (an EC2 instance in your cluster) where pods actually execute.

bash — nodes inspection 
# List worker nodes
kubectl get nodes

# Show additional information (Internal IP, External IP, OS image, Kernel, Container Runtime)
kubectl get nodes -o wide

# Get detailed resource capacity, conditions, and allocated pods of a node
kubectl describe node <node-name>

2. Pods

A pod is the smallest deployable unit in Kubernetes. It typically runs one application container (such as our React/Nginx web server), although it can contain multiple co-located containers sharing localhost networking and volumes.

bash — pods inspection & logs 
# List pods in default namespace
kubectl get pods

# List pods across all namespaces (includes kube-system core add-ons)
kubectl get pods -A

# Show detailed pod status, restart counts, mount paths, and lifecycle events
kubectl describe pod <pod-name>

# Watch pods in real-time as their status changes (e.g., ContainerCreating → Running)
kubectl get pods -w

# View application stdout/stderr logs
kubectl logs <pod-name>

# Stream logs live (follow mode like tail -f)
kubectl logs -f <pod-name>

3. Deployments

A Deployment manages application replicas (ReplicaSets), orchestrates zero-downtime rolling updates, and automatically replaces pods that crash or become unhealthy.

bash — deployment lifecycle 
# List active deployments
kubectl get deployments

# Get deployment configuration details and rolling update strategy
kubectl describe deployment <deployment-name>

# Scale a deployment dynamically to 3 replicas
kubectl scale deployment <deployment-name> --replicas=3

# Track the rollout progress of a new version
kubectl rollout status deployment/<deployment-name>

# Gracefully restart all pods in a deployment without downtime
kubectl rollout restart deployment/<deployment-name>

4. Services

Pods are ephemeral and can be terminated at any moment with a new IP address. A Service provides a stable network endpoint, DNS record, and built-in load balancer across a matching group of pods.

bash — service commands 
# List services
kubectl get services

# Get detailed service information and endpoint targets
kubectl describe service <service-name>

Common Service Types

Type Purpose & Accessibility
ClusterIP Internal cluster access only (default). Only other pods inside the cluster can reach this IP.
NodePort Exposes a static port (30000–32767) on each worker node’s IP address.
LoadBalancer Requests an external cloud load balancer (AWS NLB/CLB or ALB) to route public traffic to your pods.

For a web application that needs public access, a LoadBalancer Service is the most direct option. In advanced setups, an Ingress with the AWS Load Balancer Controller can also be used to route multiple domain paths through a single Application Load Balancer.

Step 6: Deploy a React Application from Amazon ECR

Now, let's tie together Docker, Amazon ECR (Elastic Container Registry), and EKS to run your actual React web frontend.

Step 6.1: Find your ECR image

List your ECR repositories to find where your container image was pushed:

bash — find ECR image 
# List all ECR repositories in your account
aws ecr describe-repositories

# List image tags in a particular repository
aws ecr list-images \
  --repository-name my-react-app

Your complete image URI follows this structure:

image URI anatomy 
123456789012.dkr.ecr.ap-south-1.amazonaws.com/my-react-app:latest

Replace the AWS account ID (123456789012), region (ap-south-1), repository name (my-react-app), and tag (latest) with your actual values.

Step 6.2: Create a Kubernetes Deployment

Create a manifest file named deployment.yaml in your project directory:

deployment.yaml 
apiVersion: apps/v1
kind: Deployment

metadata:
  name: react-app

spec:
  replicas: 2

  selector:
    matchLabels:
      app: react-app

  template:
    metadata:
      labels:
        app: react-app

    spec:
      containers:
        - name: react-container
          image: 123456789012.dkr.ecr.ap-south-1.amazonaws.com/my-react-app:latest

          ports:
            - containerPort: 80

This manifest requests 2 replica pods and assumes your compiled React static bundle is served by Nginx inside the container listening on port 80.

⚠ Crucial IAM Node Permission

Your EKS worker nodes (or Pod Identity/IRSA) must have the AmazonEC2ContainerRegistryReadOnly policy attached to their IAM Role. Otherwise, the nodes cannot authenticate to ECR, and your pods will be trapped in ImagePullBackOff.

Step 6.3: Apply the Deployment

Apply the manifest to your connected EKS cluster and observe the rollout:

bash — apply & verify deployment 
# Submit deployment recipe to EKS
kubectl apply -f deployment.yaml

# Check deployment replica status
kubectl get deployments

# Check the 2 spawned pods
kubectl get pods

# Wait until deployment is ready
kubectl rollout status deployment/react-app

If any pod is stuck in ImagePullBackOff or ErrImagePull, inspect the container events immediately:

bash — pod inspect 
kubectl describe pod <pod-name>

Step 6.4: Expose the React Application

Create a service file named service.yaml to request a public AWS Load Balancer:

service.yaml 
apiVersion: v1
kind: Service

metadata:
  name: react-service

spec:
  type: LoadBalancer

  selector:
    app: react-app

  ports:
    - port: 80
      targetPort: 80

Apply the Service and watch until AWS provides an external load balancer URL:

bash — apply & watch service 
# Submit service manifest
kubectl apply -f service.yaml

# Check service
kubectl get services

# Watch until EXTERNAL-IP changes from <pending> to an AWS ELB DNS name
kubectl get service react-service -w
Sample Finished Service NAME TYPE CLUSTER-IP EXTERNAL-IP
react-service LoadBalancer 10.100.45.12 a1b2c3d4e5...ap-south-1.elb.amazonaws.com

Once the external DNS address appears, copy it and open it in your browser: Your React application is live on the internet!

💸 Cost & Networking Note

Creating a type: LoadBalancer Service triggers AWS to provision an Elastic Load Balancer (ELB), which incurs hourly AWS charges while active. Furthermore, ensure your VPC public subnets are tagged with kubernetes.io/role/elb=1 so AWS knows where to bind public IPs.

Step 7: Troubleshooting Commands

Memorize these 8 commands. When deployments fail, pods crash, or connections hang, these commands give you the diagnostic answers within seconds:

Problem Command
Pods are not running kubectl get pods -A
Pod details and events kubectl describe pod <pod-name>
Application logs kubectl logs <pod-name>
Node problems kubectl describe node <node-name>
Deployment status kubectl rollout status deployment/<name>
Service configuration kubectl describe service <name>
Recent cluster events kubectl get events --sort-by=.metadata.creationTimestamp
Current Kubernetes context kubectl config current-context
