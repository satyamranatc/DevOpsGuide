Beginner’s guide

Git and GitHub,
explained simply.

Repositories, commits, branches and pull requests. How teams save their work, share it, and build software together without stepping on each other.

8 minute read

01

The problem we’re solving

You’re writing an essay. You save a copy called essay_final.docx. Then another, essay_final_v2.docx. Then essay_final_v2_REALLY_final.docx. A week later you can’t remember which one is the good one.

Now picture ten people editing the same essay at the same time. Copies fly around by email, changes get overwritten, and nobody knows who changed what.

Code has exactly this problem, only worse, because one small mistake can break a whole app. So developers use a tool that remembers every version, and lets many people work together safely.

That tool is Git.

In one line

Git remembers every version of your work. GitHub is the website where you keep it online and share it with others.

02

Git and GitHub are different

People mix these up all the time. They’re two separate things that work well together.

Git

A tool that lives on your computer. It tracks changes and remembers every version. It works even with no internet.

GitHub

A website that stores your Git projects online. It makes sharing, backing up and teamwork easy.

Think of it as

Git is the camera that takes the photos. GitHub is the online album where you share them.

03

The save-game idea

The easiest way to understand Git is to think of saving a video game. You can save at any moment, and go back to any save if you lose a life. Here are the words you’ll meet.

Repository

Your project folder, plus its whole history. Often called a repo.

Commit

One save point. A snapshot of your work, with a short note about what changed.

Branch

A separate copy of the timeline where you can try things safely.

Main

The official timeline. The version that everyone trusts.

Clone

Download a copy of a project from GitHub onto your computer.

Push

Send your saves from your computer up to GitHub.

Pull

Bring other people’s latest saves from GitHub down to your computer.

Pull request

A polite message saying “I made changes, please check them and add them to main.”

04

Commit

A commit is a save point. When you finish a small piece of work, you commit it and write one short sentence about what you did, like “Add login button”.

Git keeps every commit forever. If something breaks next week, you can look back through the list and return to a time when it worked.

Think of it as

A save point in a game. Save often, with a clear name, and you can always go back.

There’s a small extra step you’ll see in the diagram. Before saving, you first choose which changes go into the save. That waiting area is called the staging area. It’s like putting items in a box before you seal and label it.

05

Branch

Say your app works well and you want to try a new idea. If you experiment directly, you might break it for everyone.

So you make a branch. It’s your own side copy of the timeline. You can change anything, break anything, and the main version stays safe.

If the idea works, you merge it back into main. If it doesn’t, you throw the branch away and nothing is lost.

Think of it as

Writing in pencil on a photocopy. If you like the result, copy it onto the original. If not, bin the photocopy.

Teams usually make one branch per task: add-login, fix-payment-bug, new-homepage. Everyone works at the same time without getting in each other’s way.

06

Pull request

When your work on a branch is ready, you don’t just push it into main. You open a pull request on GitHub.

It’s a message to your team saying: “Here’s what I changed. Please take a look.” Teammates read your changes, leave comments, and ask for fixes. When everyone is happy, the changes are added to main.

This is the biggest reason teams love GitHub. A second pair of eyes catches mistakes before they reach real users. Many companies also run automatic tests on every pull request, which is where DevOps comes in.

07

The whole picture

Your work moves left to right: from a folder on your computer, into a save point, up to GitHub, and finally into main through a pull request.

08

Your first project, step by step

Here is the whole journey, from nothing to your first change on GitHub. The commands look strange at first, but you only need a handful.

  1. Make an account and a repository

    Sign up at github.com, then press New repository and give it a name. This is your online home for the project.

  2. Clone it to your computer

    This downloads the project so you can work on it locally.

    # download the project
git clone https://github.com/you/my-project.git
cd my-project

  3. Make a branch

    Give your task its own safe space.

    # create and switch to a new branch
git checkout -b add-login

  4. Change files, then save

    Edit anything you like. When you’re happy, choose the changes and save them with a short note.

    # pick the changes, then save them
git add .
git commit -m "Add login button"

  5. Push to GitHub

    Send your branch online so others can see it.

    # upload your branch
git push origin add-login

  6. Open a pull request

    On GitHub you’ll see a green Compare & pull request button. Press it, write a sentence about your change, and send it. Once your team approves, press Merge. Your work is now in main.

Later, when teammates have merged their work, run git pull to bring the latest version down to your computer.

09

Quick recap

  • Git remembers every version of your work, on your computer.
  • GitHub is the website where you store and share your Git projects.
  • A commit is a save point, with a short note.
  • A branch is a safe side copy for trying things out.
  • Push sends your saves up. Pull brings others’ saves down.
  • A pull request asks the team to review your work before it joins main.
If you remember one thing

Save often, work on a branch, and ask for a review before you merge. That’s how almost every software team works.
