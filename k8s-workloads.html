PHASE 05

Deploying Applications

In Phase 4, you learned how YAML files work. Now let's deploy, scale, update, and roll back real applications.

1. Create a Pod vs. Deploy with a Deployment

You can spin up a single Pod quickly from the terminal to test an image, but in production you always wrap your app in a Deployment so Kubernetes maintains multiple replicas and heals crashes:

# Quick one-line Pod creation (great for testing)
kubectl run nginx-test --image=nginx:alpine --port=80

# Production Deployment YAML (deployment.yaml)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: react-web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: react-web
  template:
    metadata:
      labels:
        app: react-web
    spec:
      containers:
        - name: web
          image: nginx:1.27-alpine
          ports:
            - containerPort: 80

2. Run Multiple Replicas & Expose with a Service

# Apply the Deployment and verify 3 replicas are Running
kubectl apply -f deployment.yaml
kubectl get deployments
kubectl get pods -l app=react-web

# Scale up or down dynamically
kubectl scale deployment react-web --replicas=5

# Expose the Deployment on port 80 and test in your browser locally
kubectl expose deployment react-web --type=LoadBalancer --port=80
kubectl port-forward svc/react-web 8080:80
# Now open http://localhost:8080 in your browser!

3. Update an Application Image, Rollout & Rollback

When you release version 2.0 of your app, Kubernetes performs a Rolling Update—starting new v2.0 pods and waiting until they are healthy before terminating old v1.0 pods. Zero visitors ever see an error page.

# 1. Update the container image to a new version
kubectl set image deployment/react-web web=nginx:1.28-alpine

# 2. Watch the live rolling update progress
kubectl rollout status deployment/react-web

# 3. View revision history
kubectl rollout history deployment/react-web

# 4. Instant rollback to the previous working version if v2 has a bug!
kubectl rollout undo deployment/react-web
PHASE 06

Networking Basics

Kubernetes networking is built on one simple rule: Every Pod gets its own unique IP address inside the cluster, and every Pod can talk to every other Pod directly without NAT.

However, because Pods die and respawn with new IP addresses, you never hardcode a Pod IP. Instead, you use Services, CoreDNS, and Ingress.

1. The 3 Service Types Compared

Service Type How It Works & When to Use It
ClusterIP
(Default)		 Creates a private internal IP reachable only inside the cluster. Use this for backend APIs, Redis caches, and databases that the public internet should never touch directly.
NodePort Opens a static port (between 30000–32767) on every Worker Node’s IP address. Traffic hitting NodeIP:30080 is forwarded to your Pods. Great for local testing or custom on-prem proxies.
LoadBalancer Instructs your cloud provider (AWS, GCP, Azure) to provision an external Cloud Load Balancer (AWS ELB/NLB) with a public DNS name that routes internet traffic straight to your Service.

2. Service Discovery & DNS in Kubernetes (CoreDNS)

Every Kubernetes cluster runs a built-in DNS server called CoreDNS. The moment you create a Service named orders-api in the default namespace, CoreDNS automatically registers a DNS record for it:

How microservices talk to each other

Your React or Node app simply calls http://orders-api (or http://orders-api.default.svc.cluster.local across namespaces). CoreDNS resolves that name to the Service’s steady ClusterIP automatically.

3. Introduction to Ingress (One Smart Front Door)

Each type: LoadBalancer Service creates a separate AWS Load Balancer (~$18/month each). If you have 10 microservices, paying for 10 separate cloud load balancers is wasteful.

An Ingress sits in front of multiple ClusterIP Services and routes HTTP/HTTPS traffic using domain names and URL paths through a single cloud load balancer (powered by an Ingress Controller like the AWS Load Balancer Controller or NGINX Ingress):

# Example: Ingress routing / to React frontend and /api to Express backend
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
spec:
  rules:
    - host: myapp.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: react-web
                port:
                  number: 80
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: orders-api
                port:
                  number: 3000

PHASE 07

Storage Basics: Volumes, PV, PVC & AWS EBS

By default, container filesystems are ephemeral (temporary). When a Pod crashes or gets replaced during a rollout, every file written inside that container is wiped clean.

That is fine for stateless web servers (like React or Nginx), but fatal for databases or file uploads. Kubernetes solves this with four storage abstractions:

1. Volume

A directory mounted into a Pod (such as emptyDir) that lets containers share files for the lifetime of that Pod.

2. PersistentVolume (PV)

The Actual Hard Drive. A piece of real cluster storage (like an AWS EBS disk or NFS share) whose lifecycle is completely independent of any Pod.

3. PersistentVolumeClaim (PVC)

The Storage Voucher / Request. A developer writes a PVC saying: “My Pod needs 20Gi of fast SSD storage.” Kubernetes binds the PVC to a matching PV.

4. StorageClass

The Automated Provisioner. Instead of an admin manually creating PVs, a StorageClass (like ebs-sc / gp3 on AWS EKS) dynamically creates a brand-new AWS EBS hard drive on demand whenever a Pod submits a PVC.

Example: Requesting AWS EBS Storage with a PVC

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data-pvc
spec:
  accessModes:
    - ReadWriteOnce        # Mounted by a single node at a time (standard for AWS EBS)
  storageClassName: gp3    # Uses the AWS EBS CSI Driver to create a gp3 SSD volume
  resources:
    requests:
      storage: 10Gi
PHASE 08

Configuration, Resources & Health Probes

Production-ready Kubernetes deployments require three finishing touches: externalized configuration (ConfigMaps & Secrets), hardware guardrails (Requests & Limits), and automated health checks (Liveness & Readiness Probes).

1. Environment Variables, ConfigMaps & Secrets

ConfigMap · Plain Config

Holds non-secret settings (LOG_LEVEL=info, API_URL). Create via YAML or CLI:
kubectl create configmap app-config --from-literal=API_URL=https://api.myapp.com

Secret · Sensitive Credentials

Holds passwords and API keys (base64-encoded in etcd, encrypted at rest in EKS):
kubectl create secret generic db-secret --from-literal=DB_PASS=s3cr3t!

2. CPU and Memory Requests vs. Limits

Without resource boundaries, a single memory-leaking container can starve the entire Worker Node and crash neighboring apps:

  • Requests (Guaranteed Minimum): How much CPU/RAM the container is guaranteed to get. The Scheduler uses requests to decide which Worker Node has enough room for the Pod.
  • Limits (Hard Ceiling): The maximum CPU/RAM the container is allowed to consume. If a container exceeds its CPU limit, it is throttled; if it exceeds its memory limit, it is terminated with OOMKilled (Out Of Memory).

3. Liveness Probes vs. Readiness Probes

Readiness Probe · "Can I take traffic?"

Checks if the container has finished booting and loading caches. If it fails, Kubernetes removes the Pod from the Service load balancer until it recovers (without restarting it).

Liveness Probe · "Am I deadlocked?"

Checks if the app is still alive and responsive. If a Liveness probe fails repeatedly, Kubernetes kills and restarts the container automatically to heal the deadlock.

Complete Production Deployment YAML (Combining All of Phase 8)

apiVersion: apps/v1
kind: Deployment
metadata:
  name: production-api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: production-api
  template:
    metadata:
      labels:
        app: production-api
    spec:
      containers:
        - name: api
          image: 123456789012.dkr.ecr.ap-south-1.amazonaws.com/orders-api:1.2
          ports:
            - containerPort: 3000

          # 1. Inject ConfigMap & Secret as Environment Variables
          env:
            - name: API_URL
              valueFrom:
                configMapKeyRef:
                  name: app-config
                  key: API_URL
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-secret
                  key: DB_PASS

          # 2. CPU & Memory Requests and Limits
          resources:
            requests:
              cpu: "100m"       # 0.1 CPU core guaranteed
              memory: "128Mi"   # 128 MB RAM guaranteed
            limits:
              cpu: "500m"       # Max 0.5 CPU core
              memory: "256Mi"   # Max 256 MB RAM (OOMKilled above this)

          # 3. Readiness & Liveness Health Probes
          readinessProbe:
            httpGet:
              path: /healthz
              port: 3000
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /healthz
              port: 3000
            initialDelaySeconds: 15
            periodSeconds: 20
RECAP

Quick recap: Phases 5–8

  • Use Deployments to manage replicas, perform zero-downtime rolling updates, and roll back broken releases with kubectl rollout undo.
  • ClusterIP is for internal traffic, NodePort opens a static node port, and LoadBalancer provisions a cloud load balancer.
  • Ingress routes multiple hostnames and paths (/ and /api) through a single cloud load balancer, while CoreDNS provides automatic internal DNS names.
  • PVCs request persistent storage from a StorageClass (like AWS EBS gp3) so database files survive Pod restarts.
  • Use ConfigMaps and Secrets for configuration, Requests/Limits to prevent resource starvation, and Readiness/Liveness Probes for traffic safety and auto-healing.
