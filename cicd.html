Beginner’s project guide

CI/CD with GitHub Actions,
explained simply.

Push your code, and a robot tests it, packs it into Docker, and puts it live on EC2 behind Nginx. We’ll build the whole thing for a small React and Express app.

Before you start

This guide builds on the others. It helps to have read Git & GitHub, Docker, EC2 and Nginx. You’ll also need free accounts on GitHub, Docker Hub and AWS, and Node 20 on your computer.

01

The goal

Right now, putting a change live probably means: test it, build it, log in to the server, copy files, restart things, and hope you didn’t forget a step. Do that ten times a day and you’ll make mistakes.

We want this instead:

The dream

You run git push. A few minutes later, your change is live. Nothing else to do.

That’s CI/CD, and GitHub Actions is the free robot on GitHub that does it for you. It watches your repository, and whenever you push, it runs the steps you wrote down.

02

The delivery-van idea

Think of a small factory that makes a product and ships it to a shop. Each CI/CD word fits somewhere in that story.

CI

Continuous Integration. Every time someone adds code, it’s automatically built and tested. Like quality control on the factory floor.

CD

Continuous Delivery or Deployment. Code that passes the checks is automatically sent live. Like the van that drives to the shop.

Pipeline

The whole assembly line, from your push to the live site.

Workflow

GitHub’s name for one pipeline. It’s a single file of instructions, written in YAML.

Job

One stage of the line, such as “test” or “deploy”. Each job runs on its own fresh computer.

Step

One small action inside a job, like “install packages”.

Runner

The temporary computer GitHub lends you to run a job. It’s wiped when the job ends.

Secret

A password or key stored safely in GitHub. Your workflow can use it, but nobody can read it.

Docker Hub

The warehouse between factory and shop. Built images wait here to be collected.

03

The whole picture

This is the pipeline we’re building. Follow it from the top left: you push, the robot tests and builds, the images go to Docker Hub, and EC2 pulls and runs them.

04

The app

We need something small to deploy: a React page that shows a message from an Express API. Make a folder for the whole project, and create this layout inside it.

myapp/
├── server/                 # Express API
│   ├── app.js
│   ├── index.js
│   ├── app.test.js
│   ├── package.json
│   ├── Dockerfile
│   └── .dockerignore
├── client/                 # React app (made with Vite)
│   ├── src/App.jsx
│   ├── vite.config.js
│   ├── nginx.conf
│   ├── Dockerfile
│   └── .dockerignore
├── compose.local.yaml      # for testing on your laptop
└── .github/workflows/deploy.yml

The Express API

Inside server/, run npm init -y and npm install express. Then set the scripts in package.json:

// server/package.json  (the "scripts" part)
"scripts": {
  "start": "node index.js",
  "test": "node --test"
}

We split the app in two files. app.js describes the routes. index.js starts listening. This lets the tests use the app without starting a real server.

// server/app.js
const express = require('express');
const app = express();

app.get('/api/health', (req, res) => {
  res.json({ status: 'ok' });
});

app.get('/api/hello', (req, res) => {
  res.json({ message: 'Hello from Express, deployed automatically!' });
});

module.exports = app;
// server/index.js
const app = require('./app');
const port = process.env.PORT || 3000;

app.listen(port, () => console.log('API listening on port ' + port));

A test, so CI has something to check

This uses Node’s built-in test tool, so there’s nothing extra to install.

// server/app.test.js
const test = require('node:test');
const assert = require('node:assert');
const app = require('./app');

test('health endpoint answers ok', async () => {
  const server = app.listen(0);
  const { port } = server.address();

  const res = await fetch('http://127.0.0.1:' + port + '/api/health');
  const body = await res.json();

  assert.strictEqual(res.status, 200);
  assert.strictEqual(body.status, 'ok');
  server.close();
});

Check it passes on your computer. Then try the server:

cd server
npm test
npm start
# in another terminal:
curl http://localhost:3000/api/hello

The React app

From the project folder, make the client with Vite:

npm create vite@latest client -- --template react
cd client
npm install

Replace src/App.jsx with a page that calls the API:

// client/src/App.jsx
import { useEffect, useState } from 'react'

export default function App() {
  const [message, setMessage] = useState('Loading...')

  useEffect(() => {
    fetch('/api/hello')
      .then((res) => res.json())
      .then((data) => setMessage(data.message))
      .catch(() => setMessage('Could not reach the API'))
  }, [])

  return <h1>{message}</h1>
}

While developing, Vite needs to forward /api calls to Express. Set that in vite.config.js:

// client/vite.config.js
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [react()],
  server: {
    proxy: { '/api': 'http://localhost:3000' },
  },
})

Run npm run dev in client (with the API running too), and your page shows the message from Express. Notice that React calls the plain path /api/hello, with no server address. In production, Nginx will handle that path, which is why it all fits together.

Commit the lock files

Make sure package-lock.json in both folders is committed to Git. The pipeline uses npm ci, which needs it, and it guarantees the same versions everywhere.

05

Put it in Docker

Each part gets its own image: one for Express, one for React plus Nginx. If Docker is new, the Docker guide explains every word here.

The API image

# server/Dockerfile
FROM node:20-alpine
WORKDIR /app

# install packages first, so Docker can reuse this step
COPY package*.json ./
RUN npm ci --omit=dev

COPY . .
EXPOSE 3000
CMD ["node", "index.js"]
# server/.dockerignore  (and the same in client/)
node_modules
npm-debug.log
.git

The web image, in two stages

React has to be built into plain files before it can be served. The first stage builds it with Node. The second stage throws Node away and keeps only Nginx and the built files, which makes the final image small.

# client/Dockerfile
# stage 1: build the React app
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# stage 2: serve it with Nginx
FROM nginx:alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80

The Nginx config

This is the front door from the Nginx guide. It serves the React files, and passes /api to the Express container. Inside Docker, containers find each other by service name, so the API is simply api.

# client/nginx.conf
server {
    listen 80;
    root /usr/share/nginx/html;
    index index.html;

    # anything starting with /api goes to Express
    location /api/ {
        proxy_pass http://api:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # everything else is the React app
    location / {
        try_files $uri /index.html;
    }
}

The line try_files $uri /index.html sends unknown paths back to the React app, which is what lets React handle its own pages.

Test it all on your laptop first

A small compose file in the project root builds both images and runs them together:

# compose.local.yaml
services:
  api:
    build: ./server

  web:
    build: ./client
    ports:
      - "8080:80"
    depends_on:
      - api
docker compose -f compose.local.yaml up --build

Open http://localhost:8080. You should see “Hello from Express, deployed automatically!”. If so, the Docker part is finished. Press Ctrl+C and run docker compose -f compose.local.yaml down to stop.

06

Set up Docker Hub

The robot needs somewhere to leave the built images, and the server needs somewhere to collect them. That’s Docker Hub.

  1. Make an account

    Sign up at hub.docker.com. Your username becomes part of every image name, such as yourname/myapp-api.

  2. Create an access token

    Go to Account settings → Personal access tokens and create one with Read & Write permission. Copy it now, because it’s only shown once. We use a token instead of your password, so it can be cancelled any time without changing your login.

  3. Nothing else to prepare

    The repositories myapp-api and myapp-web are created automatically the first time the pipeline pushes to them. Note that new repositories are public by default, so never put passwords or secrets inside an image.

07

Set up the EC2 server

The server only needs Docker and a small file. It won’t build anything. It just pulls ready-made images, so even a small t3.micro is fine.

Step 1 · Launch the instance

Follow the EC2 guide with these choices:

  • Ubuntu as the image. The login username is ubuntu.
  • t3.micro as the size, with the key pair you already made.
  • A security group that allows SSH (22) and HTTP (80).

Step 2 · Install Docker

Log in with ssh -i my-key.pem ubuntu@YOUR-IP, then run:

# install Docker and the compose plugin
curl -fsSL https://get.docker.com | sudo sh

# let the ubuntu user run docker without sudo
sudo usermod -aG docker ubuntu

Now log out and log back in, so the new permission applies. Check it with:

docker --version
docker compose version

Step 3 · Make a deploy key

The robot needs its own key to log in. Don’t reuse your personal one. On your laptop, make a fresh pair:

ssh-keygen -t ed25519 -f deploy_key -C "github-actions" -N ""

This creates deploy_key (private) and deploy_key.pub (public). Add the public half to the server:

cat deploy_key.pub | ssh -i my-key.pem ubuntu@YOUR-IP \
  'cat >> ~/.ssh/authorized_keys'

Test that it works, with no password asked:

ssh -i deploy_key ubuntu@YOUR-IP "echo it works"

Step 4 · Add the compose file

On the server, make a folder and a file. This is the file that decides what runs. Replace yourname with your Docker Hub username.

mkdir -p ~/myapp
nano ~/myapp/docker-compose.yml
# ~/myapp/docker-compose.yml  (on the server)
services:
  api:
    image: yourname/myapp-api:latest
    restart: unless-stopped

  web:
    image: yourname/myapp-web:latest
    restart: unless-stopped
    ports:
      - "80:80"
    depends_on:
      - api

restart: unless-stopped brings your containers back automatically if the server reboots or a container crashes. Only the web container is exposed to the outside, on port 80. The API stays hidden behind it.

08

Give GitHub the keys

The workflow needs five pieces of private information. Never write these in the file itself. Store them as secrets.

Push your project to a new GitHub repository first. Then open it and go to Settings → Secrets and variables → Actions → New repository secret, and add these five:

DOCKERHUB_USERNAME

Your Docker Hub username.

DOCKERHUB_TOKEN

The access token you copied from Docker Hub.

EC2_HOST

Your server’s public IP address.

EC2_USER

The login name: ubuntu.

EC2_SSH_KEY

The whole contents of the private file deploy_key, including the BEGIN and END lines.

To copy the key on a Mac, run pbcopy < deploy_key, then paste. Once saved, GitHub never shows a secret again, which is the point.

Keep it safe

Never commit deploy_key or your .pem file to Git. After adding the secret, you can delete the local copy of deploy_key.

09

Write the workflow

Now the main event. Create this file exactly at .github/workflows/deploy.yml. The folder names matter, because GitHub only looks there.

# .github/workflows/deploy.yml
name: CI/CD

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  # 1 · check the code works
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
          cache-dependency-path: |
            server/package-lock.json
            client/package-lock.json

      - name: Test the API
        working-directory: server
        run: |
          npm ci
          npm test

      - name: Build the React app
        working-directory: client
        run: |
          npm ci
          npm run build

  # 2 · build images and upload them to Docker Hub
  build-and-push:
    needs: test
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Build and push the API image
        uses: docker/build-push-action@v6
        with:
          context: ./server
          push: true
          tags: |
            ${{ secrets.DOCKERHUB_USERNAME }}/myapp-api:latest
            ${{ secrets.DOCKERHUB_USERNAME }}/myapp-api:${{ github.sha }}

      - name: Build and push the web image
        uses: docker/build-push-action@v6
        with:
          context: ./client
          push: true
          tags: |
            ${{ secrets.DOCKERHUB_USERNAME }}/myapp-web:latest
            ${{ secrets.DOCKERHUB_USERNAME }}/myapp-web:${{ github.sha }}

  # 3 · log in to EC2 and start the new version
  deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    steps:
      - name: Deploy over SSH
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.EC2_HOST }}
          username: ${{ secrets.EC2_USER }}
          key: ${{ secrets.EC2_SSH_KEY }}
          script: |
            cd ~/myapp
            docker compose pull
            docker compose up -d
            docker image prune -f

What each part does

on:

When to run. Every push to main, and every pull request aimed at main.

test

Runs on every push and pull request. Checks out your code, installs packages, runs the API test and makes sure React builds. This is the CI part.

needs:

Order. “Don’t start until that job has passed.” If the tests fail, nothing after them runs.

if:

Only build and deploy for pushes to main. Pull requests get tested, but never deployed.

build-and-push

Logs in to Docker Hub, builds both images, and uploads each with two tags: latest, and the exact commit ID so you can always find an old version.

deploy

Connects to EC2, pulls the new images, restarts only what changed, and deletes old unused images to save disk space. This is the CD part.

${{ secrets.X }}

How the file reads a secret, without ever showing it.

10

Watch it deploy

Time for the first run. From your project folder:

git add .
git commit -m "Add CI/CD pipeline"
git push origin main

  1. Open the Actions tab

    On your repository page, click Actions. You’ll see a run called “Add CI/CD pipeline”, with a spinning yellow dot.

  2. Watch the three jobs

    Click the run. test goes first, then build-and-push, then deploy. Each turns into a green tick. Click any job to read its live log.

  3. Check Docker Hub

    Your two repositories, myapp-api and myapp-web, now appear with fresh images.

  4. Open your site

    Visit http://YOUR-IP in a browser. You should see “Hello from Express, deployed automatically!”.

Check from the server too

ssh -i my-key.pem ubuntu@YOUR-IP

cd ~/myapp
docker compose ps             # both containers should be "running"
docker compose logs api       # what Express has printed
curl http://localhost/api/hello

Now make a change

This is the moment it clicks. Edit the message in server/app.js, then push:

# change the text in server/app.js, then:
git add .
git commit -m "Change the greeting"
git push origin main

Watch the Actions tab turn green again. A couple of minutes later, refresh your site, and the new message is live. You never logged in to the server.

That’s CI/CD

Edit, commit, push. The robot tests it, packs it, ships it and starts it.

11

Rollbacks

Say a bad change went live. Because every image was also tagged with its commit ID, you can go back. Find the ID of the last good commit with git log --oneline, but note that the tag is the full 40-character ID, which you can copy from the commit page on GitHub.

On the server, edit docker-compose.yml to use that tag instead of latest:

image: yourname/myapp-api:3f2a9c1e5b7d...   # the full commit ID
docker compose pull
docker compose up -d

Once you’ve fixed the problem and pushed, change the file back to latest. A common alternative is to revert the bad commit in Git and push, so the pipeline redeploys the old code for you.

12

Make it safer

What we built works, and it’s a solid start. Before using it for anything real, know about these limits.

Worth knowing

GitHub’s runners connect from many changing addresses, so for this setup, port 22 must be open to the internet. The SSH key is the only lock. Use a dedicated key (as we did), and never allow password logins.

Close port 22

For a stricter setup, deploy with AWS Systems Manager, or a self-hosted runner, so SSH needn’t be open to everyone.

Add HTTPS

Point a domain at the server and add a certificate. The Nginx guide shows how, with Certbot.

Protect main

In repository settings, require pull requests and passing tests before anything can be merged.

Run real tests

One health test is a start. Add more as the app grows, since the pipeline is only as good as its tests.

Keep secrets out

Pass passwords to containers as environment variables on the server. Never bake them into an image.

Go faster

Add Docker layer caching to build-push-action so repeat builds take seconds instead of minutes.

13

When things go wrong

The Actions tab shows exactly which step failed, with its full log. Start there every time.

The workflow never starts

The file must be at exactly .github/workflows/deploy.yml, and you must push to main. If your branch is called master, change it in the file.

“npm ci can only install with a lock file”

You didn’t commit package-lock.json in server or client. Commit both.

Docker login fails

Check DOCKERHUB_USERNAME and DOCKERHUB_TOKEN, with no extra spaces. Make sure the token has write permission.

“denied: requested access to the resource is denied”

The image name doesn’t start with your Docker Hub username, or the token can’t write. Check the secrets.

Deploy step times out

The server can’t be reached. Check EC2_HOST is the right IP, and that port 22 is open. Remember a stopped and started instance gets a new IP.

SSH: “Permission denied (publickey)”

Wrong user or key. EC2_USER is ubuntu, and EC2_SSH_KEY must hold the whole private key, including the BEGIN and END lines.

“permission denied” running docker on the server

You skipped usermod, or didn’t log out and back in afterwards.

502 Bad Gateway on the site

Nginx is up but Express isn’t. Run docker compose logs api to see why it crashed.

The old version is still showing

Check the deploy job finished green, then hard-refresh your browser. On the server, docker compose ps shows how long the containers have been up.

Server out of disk space

Old images pile up. The workflow already prunes them. To clean more, run docker system prune.

14

Quick recap

  • CI tests every change. CD ships the ones that pass.
  • A workflow is one YAML file in .github/workflows, made of jobs and steps.
  • Our pipeline has three jobs: test, build-and-push, deploy.
  • Two images, api (Express) and web (React + Nginx), go to Docker Hub.
  • EC2 only runs docker compose pull and up -d. It never builds.
  • Passwords and keys live in GitHub secrets, never in the code.
  • Tag images with the commit ID, so you can roll back.
If you remember one thing

Automate the boring, error-prone steps once, and every push after that is safe, fast and identical.
