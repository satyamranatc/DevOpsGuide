01

What Nginx is

When you type a website address, your browser asks a server for a page. Something on that server has to listen for the request and send the right thing back. That something is a web server.

Nginx (say “engine-x”) is one of the most popular web servers in the world. It’s fast, light on memory, and free. A huge share of the internet’s busiest sites run through it.

It does three jobs, and you’ll learn all of them:

  • Web server. Hands out files such as pages, images and styles.
  • Reverse proxy. Sits in front of your app and passes requests to it.
  • Load balancer. Spreads visitors across several copies of your app.
In one line

Nginx stands at the front of your server, listens for visitors, and sends each one to the right place.

02

The restaurant host idea

Picture the person who greets you at a restaurant door. They don’t cook. They welcome you and take you to the right table. Nginx works the same way.

Nginx

The host at the door. Greets every visitor and decides where they go.

Static file

A ready-made dish, like a page, image or stylesheet. The host can hand it over straight away.

Your app

The kitchen. It cooks dishes to order, such as a login or a search.

Reverse proxy

The host carrying orders to the kitchen and bringing the food back. Guests never see the kitchen.

Port

A numbered door. Websites use 80 for plain web and 443 for secure web.

Server block

One restaurant’s rules. Lets one Nginx look after several websites.

Location

A rule for one part of the menu: “for /api, go to the kitchen”.

HTTPS

A sealed envelope. Nobody on the way can read what’s inside.

03

Install and check it

Log in to a Linux server, such as the one from the EC2 guide. Then install Nginx with the tool your system uses.

# Amazon Linux
sudo dnf install -y nginx

# Ubuntu or Debian
sudo apt update
sudo apt install -y nginx

Start it, and make sure it starts again whenever the server reboots:

sudo systemctl enable --now nginx

# is it running?
sudo systemctl status nginx

# ask it for the home page, from the server itself
curl http://localhost

You’ll see a short “Welcome to nginx!” page. Open your server’s public address in a browser and you’ll see the same. If it doesn’t load from outside, check the firewall (the security group on AWS) allows port 80.

Where things live

/etc/nginx/nginx.conf

The main settings file. You rarely need to change it.

/etc/nginx/conf.d/

Your own site files go here. Every .conf file in this folder is loaded.

/var/log/nginx/

Two logs: access.log (who visited) and error.log (what went wrong).

/usr/share/nginx/html

The default folder of web pages on Amazon Linux. On Ubuntu it’s /var/www/html.

04

Reading a config file

Nginx is controlled by plain text files. They look odd at first, but they’re made of just two things: settings that end in a semicolon, and blocks in curly braces that group them.

Here’s a complete, tiny website:

server {
    listen 80;
    server_name example.com;

    root /var/www/mysite;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}

Line by line:

  • server { } is one website’s rules.
  • listen 80 means “answer on port 80”.
  • server_name is the address this site answers to. Use your domain, or an underscore _ for “anything”.
  • root is the folder holding your website’s files.
  • index is the file to show when no page is named.
  • location / is the rule for every address. try_files looks for a matching file, and shows a 404 if there isn’t one.
The safety habit

After every change, test first with sudo nginx -t. If it says “syntax is ok”, apply it with sudo systemctl reload nginx. A reload swaps in the new rules without dropping anyone.

05

Serve your own website

Let’s replace the welcome page with your own. First make a folder and a page:

sudo mkdir -p /var/www/mysite

echo "<h1>My site, served by Nginx!</h1>" | sudo tee /var/www/mysite/index.html

Now create the config file, /etc/nginx/conf.d/mysite.conf:

sudo nano /etc/nginx/conf.d/mysite.conf

Paste in this, then save and exit:

server {
    listen 80 default_server;
    server_name _;

    root /var/www/mysite;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}

On Ubuntu, remove its built-in default site, so the two don’t clash:

sudo rm /etc/nginx/sites-enabled/default

Finally, test and apply:

sudo nginx -t
sudo systemctl reload nginx
curl http://localhost
# <h1>My site, served by Nginx!</h1>

On Amazon Linux, the built-in config also has a default server on port 80. If you still see the welcome page, comment out its server { } block in /etc/nginx/nginx.conf, then reload again.

06

Reverse proxy

Here’s the job Nginx is used for most. Your app (Node, Python, Java, anything) listens on a port like 3000. You don’t want people hitting that directly. Instead, Nginx takes the request on port 80 and passes it on to your app, then returns the answer.

Why it’s worth it

One front door for many apps. HTTPS in one place. Your app stays hidden. Static files are served fast.

What you need

An app running on a port. The one from the Docker guide works well.

Start an app on port 3000. If you built the Docker image, this does it:

docker run -d -p 3000:3000 --name hello hello-app

# check it answers directly
curl http://localhost:3000

Now change the config so Nginx passes everything to it. Replace the location block in your mysite.conf:

server {
    listen 80 default_server;
    server_name _;

    location / {
        proxy_pass http://127.0.0.1:3000;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

The proxy_pass line is the heart of it: “send this to that address”. The proxy_set_header lines pass along who the real visitor was, so your app doesn’t think every request came from Nginx.

sudo nginx -t && sudo systemctl reload nginx
curl http://localhost
# Hello from my first container!

Port 80 now reaches your app on port 3000, and you can close port 3000 to the outside world.

Different paths, different places

You can have several location rules. For example, files from a folder, and anything starting with /api to the app:

location / {
    root /var/www/mysite;
    try_files $uri $uri/ =404;
}

location /api/ {
    proxy_pass http://127.0.0.1:3000/;
}
07

Share the load

One copy of your app can only handle so many visitors. Run two or more copies, and Nginx can share the visitors between them. This is load balancing.

You list the copies in an upstream group, and point proxy_pass at the group’s name. This goes above your server block:

upstream my_app {
    server 127.0.0.1:3000;
    server 127.0.0.1:3001;
}

server {
    listen 80 default_server;

    location / {
        proxy_pass http://my_app;
        proxy_set_header Host $host;
    }
}

By default, Nginx hands out visitors in turn: first to one, then the other. It also notices when a copy stops answering, and stops sending visitors to it for a while.

(nothing)

Round robin. Take turns. The default, and fine for most apps.

least_conn;

Send to whichever copy is least busy right now.

ip_hash;

The same visitor always goes to the same copy. Useful if the app remembers users in memory.

Add one of these words as the first line inside the upstream block to change the style.

08

The whole picture

One Nginx at the front does all three jobs. Each rule decides where a request goes: a folder of files, one app, or a group of apps that take turns.

09

Add HTTPS

Plain http sends everything in the open. HTTPS scrambles it, so no one in between can read it. Browsers also warn people away from sites without it.

To get HTTPS you need a certificate. A free tool called Certbot gets one from Let’s Encrypt and edits your Nginx config for you.

Before you start

  • You need a domain name, such as mysite.com.
  • The domain’s A record must point to your server’s public IP.
  • Ports 80 and 443 must be open in your firewall or security group.
  • Your config’s server_name should be your domain, not an underscore.

Get the certificate

# Ubuntu
sudo apt install -y certbot python3-certbot-nginx

# Amazon Linux
sudo dnf install -y certbot python3-certbot-nginx

# get a certificate and let Certbot update Nginx
sudo certbot --nginx -d mysite.com -d www.mysite.com

Answer the questions, and choose to redirect HTTP to HTTPS when asked. Certbot adds the certificate lines to your config and reloads Nginx. Visit https://mysite.com and look for the padlock.

Renewal is automatic

Certificates last about 90 days. Certbot sets up automatic renewal for you. You can check it works with a practice run:

sudo certbot renew --dry-run
10

Handy settings

Three small additions that help almost every site. Put them inside your server block.

Make pages smaller with compression

gzip on;
gzip_types text/css application/javascript application/json image/svg+xml;

Let browsers remember images and styles

This tells browsers to keep these files for 30 days, so repeat visits are much faster.

location ~* \.(css|js|png|jpg|jpeg|gif|svg|ico|woff2)$ {
    expires 30d;
}

Allow bigger file uploads

Nginx rejects uploads over 1 MB by default. Raise the limit if your app takes files.

client_max_body_size 10m;

As always: nginx -t, then reload.

11

Commands to remember

sudo nginx -t

Test your config for mistakes. Do this before every reload.

sudo systemctl reload nginx

Apply config changes without dropping visitors.

sudo systemctl restart nginx

Stop and start it. Only when a reload isn’t enough.

sudo systemctl status nginx

Is it running? Shows recent messages.

sudo systemctl stop nginx

Turn it off.

nginx -v

Show the installed version.

sudo nginx -T

Test, and print the whole combined config.

sudo tail -f /var/log/nginx/error.log

Watch errors live. Your best debugging friend.

sudo tail -f /var/log/nginx/access.log

Watch visitors arrive.

12

When things go wrong

502 Bad Gateway

Nginx works, but your app doesn’t answer. Is the app running? Is the port in proxy_pass right? Test with curl http://127.0.0.1:3000.

404 Not Found

Nginx can’t find the file. Check root points to the right folder and the file exists there.

403 Forbidden

Nginx isn’t allowed to read the folder, or there’s no index file. Check permissions and the index line.

“nginx: configuration file test failed”

A typo. The message names the file and line number. A missing semicolon is the usual cause.

I still see the “Welcome to nginx” page

The default site is still winning. Remove it (Ubuntu) or comment out the default server (Amazon Linux), then reload.

My changes do nothing

You forgot to reload. Run sudo nginx -t, then sudo systemctl reload nginx.

Works on the server, not from my laptop

The firewall or security group is blocking port 80 or 443.

Where to look first

Nine times out of ten, the answer is in /var/log/nginx/error.log. Read the last few lines before you change anything.

13

Quick recap

  • Nginx is the front door of your server. It listens and sends each visitor to the right place.
  • As a web server, it serves files from a folder.
  • As a reverse proxy, it passes requests to your app with proxy_pass.
  • As a load balancer, it shares visitors across copies listed in an upstream.
  • Certbot adds free HTTPS in one command.
  • Always nginx -t first, then reload.
  • When stuck, read error.log.
If you remember one thing

Visitors only ever talk to Nginx. Your job is to tell it, in a small file, where each kind of request should go.
