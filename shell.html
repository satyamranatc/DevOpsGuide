01

The problem we’re solving

Imagine you have to deploy a new version of your website to a remote cloud server. Here is what you type by hand every single afternoon:

Connect to the server. Check available disk space. Pull the latest code from GitHub. Run npm install. Run the tests. Restart the Nginx web server. Check if the website answers back. If anything fails, write a note in a log file.

Doing that by hand takes ten minutes. If you misspell one command, you might delete the wrong folder or crash the live site. Doing it on ten servers is impossible.

A shell script is simply a text file containing those exact commands in order. You run that single file, and your computer executes them all in two seconds without typos.

In one line

A shell script is a to-do list for your server. You write the steps once, and the computer carries them out identically every time.

02

Terminal vs Shell vs Script

Beginners often hear words like terminal, console, bash, and shell used interchangeably. They do different jobs, and picturing an office makes them obvious.

Terminal

The telephone window. It doesn’t understand commands; it just sends your keystrokes and displays the text that comes back.

Shell

The interpreter on the other end of the line (usually Bash or Zsh). It reads your words, translates them for the operating system, and returns the result.

Shell Script

An answering machine tape. A file containing 10, 50, or 100 commands saved in advance so the shell plays them all back automatically.

Think of it as

The terminal is the screen and keyboard. The shell is the chef listening to orders. The script is a printed recipe card you hand to the chef.

03

The core words you need

You don't need a computer science degree to automate DevOps tasks. 90% of all production shell scripts rely on just seven fundamental concepts:

Shebang (#!/bin/bash)

The very first line of a script. Tells the system which interpreter program to use to read the file.

Variable

A labelled cardboard box holding a value (like APP_DIR="/var/www") so you can reuse it everywhere.

Arguments ($1, $2)

Extra inputs you pass when calling the script, like ./deploy.sh production where $1 is production.

Exit code ($?)

The hidden report card every command leaves behind: 0 means success, any other number means error.

Pipe (|)

Connects two commands: takes the output of the first and pours it directly into the input of the second.

Redirection (> and >>)

Sends command output into a file instead of your screen. > overwrites; >> appends to the end.

Cron

A built-in Linux alarm clock that runs your script on a schedule (e.g. every midnight or every 5 minutes).

04

Your first script & permissions

Creating a script is as simple as creating any text file. Let's create one called hello.sh:

#!/bin/bash
# My first automated script
echo "Hello from the server!"
echo "Today is: $(date)"
echo "Current directory: $(pwd)"

Why the shebang (#!) is mandatory

The strange characters #! are called the shebang (hash-bang). When Linux sees that line at the top of a file, it knows to run /bin/bash to execute the instructions below. Without it, the operating system has to guess, which can cause erratic bugs.

The magic key: chmod +x

If you try to run your script right after creating it, Linux will block you with: Permission denied. By default, Linux protects you by forbidding newly downloaded or created text files from running as programs.

You unlock it by giving the file executable permission:

# Give execution rights to hello.sh
chmod +x hello.sh

# Run it! (The ./ means: "look in this current directory")
./hello.sh
Think of it as

Writing the script is writing a recipe. chmod +x is the official stamp of approval from the kitchen health inspector that allows the recipe to be cooked.

05

Variables, inputs and substitution

Hardcoding file paths, server names, or passwords throughout a 100-line script is dangerous. If a folder changes, you'd have to edit twenty lines. Variables let you define values once at the top.

Setting a variable

Write the name and value with NO SPACES around the = sign:
ENVIRONMENT="production"
✗ ENVIRONMENT = "production" (will fail!)

Reading a variable

Put a dollar sign $ in front of the name, and always wrap in double quotes:
echo "Deploying to: $ENVIRONMENT"

Passing arguments from the command line

You don't want to create three separate scripts for dev, staging, and production. Instead, you create one script and pass the environment as an argument:

#!/bin/bash
ENV_NAME=$1
TARGET_DIR=$2

echo "Deploying to environment: $ENV_NAME"
echo "Target path: $TARGET_DIR"

When you run ./deploy.sh prod /var/www/app, Bash automatically assigns $1="prod" and $2="/var/www/app".

$0

The name of the script itself (e.g. ./deploy.sh).

$1, $2, $3

The 1st, 2nd, and 3rd arguments passed into the script.

$#

The total number of arguments passed.

$@

All arguments passed, listed out as a list.

06

Exit codes: your safety net

Whenever a command finishes running in Linux, it leaves behind an invisible single-number status report called an exit code (or exit status). You check it using the special variable $?.

  • 0 means Perfection: The command succeeded with zero errors.
  • 1 to 255 means Failure: Something broke (file not found, out of memory, no permissions).

This is how scripts make intelligent decisions before doing something dangerous:

# Try to ping the database server
ping -c 1 db.internal.net > /dev/null 2>&1

if [ $? -eq 0 ]; then
  echo "Database is healthy. Proceeding with deployment..."
else
  echo "Error: Database is unreachable! Aborting to prevent downtime."
  exit 1
fi
The Golden Rule of exit codes

Always exit with exit 0 on success, and exit 1 on fatal errors. This lets tools like GitHub Actions or Jenkins know whether your pipeline passed or failed.

07

Loops, pipes and redirection

The true power of shell scripting comes from combining small, focused Unix utilities together using loops, pipes, and streams.

1. Looping over items

Need to restart Nginx on three different EC2 instances or check five log files? Use a for loop:

# Process a list of servers
for SERVER in "web-1" "web-2" "web-3"; do
  echo "Checking health on $SERVER..."
done

2. Pipes (|): Unix plumbing

A pipe takes the text that one program spits out and channels it straight into the next tool without writing it to disk. Here’s how to count how many Nginx worker processes are running:

# List processes → filter for 'nginx' → count lines
ps aux | grep nginx | wc -l

3. Redirection (> and >>): Saving logs

By default, script output is printed to your monitor. Redirection lets you steer that stream into a permanent log file:

# Overwrite report.txt with fresh data
echo "Deployment started" > deploy.log

# Append to the bottom without erasing existing lines
echo "Deployment finished at $(date)" >> deploy.log

09

The Golden Rules of production Bash

By default, Bash has one dangerous habit: it keeps running even when a command fails.

Imagine your script tries to change directory with cd /tmp/old_app, but the folder doesn't exist. If the very next line is rm -rf *, Bash will happily delete everything in your current directory instead!

Never write a production script without this single safety line near the top:

# The Bash safety belt
set -euo pipefail
set -e

Exit immediately if any command fails. No continuing after errors.

set -u

Treat unset variables as errors. If you misspell $DEL_PATH as $DEL_PTH, it stops immediately rather than assuming an empty string.

set -o pipefail

Prevents errors from hiding in pipes. If curl fails before grep, the whole line is marked as failed.

Always quote variables

Write rm -rf "$TARGET_DIR" instead of rm -rf $TARGET_DIR. If the directory has spaces, quotes prevent accidental disaster.

Log with timestamps

Write a small helper function log "Doing task..." that prefixes every message with the current time. Future debugging will be 10x faster.

10

Hands-on: Server health & backup script

Here is a complete, battle-tested maintenance script you can save as server_health.sh and run on any Ubuntu, Debian, or Amazon Linux EC2 server:

#!/bin/bash
# ==========================================================
# Server Health & Automated Backup Utility
# Checks disk storage, archives web logs, and checks Nginx
# ==========================================================

# 1. Turn on strict error safety
set -euo pipefail

# 2. Configuration variables
BACKUP_DIR="/var/backups/logs"
LOG_SOURCE="/var/log/nginx"
DATE_STAMP=$(date +"%Y-%m-%d_%H%M%S")
MAX_DISK_USAGE=85

log() {
  echo "[$(date '+%Y-%m-%d %H:%M:%S')] $1"
}

log "Starting daily server maintenance..."

# 3. Check disk space usage
CURRENT_USAGE=$(df / | grep / | awk '{ print $5 }' | sed 's/%//g')
log "Current root disk usage: ${CURRENT_USAGE}%"

if [ "$CURRENT_USAGE" -gt "$MAX_DISK_USAGE" ]; then
  log "WARNING: Disk space critically high! (>${MAX_DISK_USAGE}%)"
else
  log "Disk health: OK (under ${MAX_DISK_USAGE}%)"
fi

# 4. Create backup archive of web logs
mkdir -p "$BACKUP_DIR"
ARCHIVE_NAME="${BACKUP_DIR}/nginx_logs_${DATE_STAMP}.tar.gz"

if [ -d "$LOG_SOURCE" ]; then
  tar -czf "$ARCHIVE_NAME" "$LOG_SOURCE" 2>/dev/null || true
  log "Log backup created: $ARCHIVE_NAME"
fi

# 5. Check if Nginx web server is currently running
if systemctl is-active --quiet nginx; then
  log "Nginx web server is active and serving traffic."
else
  log "ALERT: Nginx is stopped! Attempting restart..."
  systemctl restart nginx || log "CRITICAL: Could not restart Nginx!"
fi

log "Maintenance completed successfully."
exit 0
How to automate this with Cron

Run crontab -e and add this line: 0 2 * * * /usr/local/bin/server_health.sh >> /var/log/health.log 2>&1. Your server will now run this script on autopilot every night at 2:00 AM.

11

10 daily commands cheatsheet

These are the ten Bash expressions you will write in DevOps scripts 95% of the time:

VAR="value"

Assign a variable (no spaces). Read it with "$VAR".

$(command)

Command substitution. Runs a command and captures its text output.

if [ -f "$FILE" ]; then

Checks if a file exists before trying to read or copy it.

if [ -d "$DIR" ]; then

Checks if a directory folder exists before writing to it.

if [ -z "$VAR" ]; then

Checks if a variable is empty or was forgotten by the user.

echo "text" >> file.log

Appends a message to the end of a log file without deleting it.

cmd 2> /dev/null

Mutes error messages (sends standard error stream to the black hole).

grep -q "text" file

Quietly searches for a pattern; check $? -eq 0 to see if found.

sleep 5

Pauses script execution for 5 seconds (great for waiting on server reboots).

exit 0 / exit 1

Terminates the script with clean success (0) or error status (1).

12

Quick recap

  • A shell script is a saved sequence of terminal commands executed by the shell.
  • Always start with the shebang #!/bin/bash so Linux knows which program interprets your file.
  • Run chmod +x your_script.sh once to give the file permission to run.
  • Store reusable text in variables (NAME="value" with no spaces) and read them with double quotes ("$NAME").
  • Every command returns an exit code: 0 is success, anything else is an error.
  • Always add set -euo pipefail at the top of production scripts to stop silent failures.
  • Use Cron to run your scripts on automatic daily or hourly schedules.
If you remember one thing

Don’t repeat manual steps. If you have to type the same sequence of commands more than twice, put it in a shell script and let the machine do the work.
